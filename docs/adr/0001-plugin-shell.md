# ADR-0001: Plugin shell — start on nice-plug, keep it thin

- Status: **Accepted (G0, 2026-10-19).** The Task 3 shell spike passed every hard must-have ([results](../spikes/shell.md)), and the test host and the UI spike found nothing against it. The editor on the real display, poly-mod in Bitwig and real audio are on the [owner checklist](../spikes/owner-checklist.md); a failure there that we can't fix in a day reopens this ADR (see the last section).
- Date: 2026-10-18 (supersedes the 2026-10-17 plan to start on clack + WebView); updated 2026-10-19 with the shell spike results; accepted at G0 on 2026-10-19

## Context

- We ship CLAP first, VST3 second, AU later. The engine and session are plain Rust libraries; the shell only translates between a host and them.
- The UI is native Rust (ADR-0002), most likely egui on baseview.
- nih-plug is in maintenance mode. Its community successor **nice-plug** (ISC) provides CLAP + VST3 export, a standalone wrapper, polyphonic modulation, state persistence, an allocation-assert debug feature, and a maintained egui adapter. It calls itself experimental and has had large recent changes. One person wrote about 89% of the commits since the fork and is the only crates.io owner, so the bus factor is 1; it has had breaking releases about monthly (the core 3 in 7 weeks, the egui adapter 5 in under 4 months). *(documented, researcher, 2026-10-19)*
- **clack** offers safe, low-level wrappers for the whole CLAP API. With clack we'd write our own parameter handling, state, GUI embedding (baseview + egui bridge), timers and VST3 path (via clap-wrapper).
- Our host-parameter design is a fixed list (8 macros + 64 automation slots), which suits a framework with declared parameters. The open question was runtime slot *renaming*.

## Decision

Start the shell on **nice-plug**, pinned to exact versions, with `Cargo.lock` committed:

| Crate | Pin | Brings |
| --- | --- | --- |
| `nice-plug` | `=0.4.2` | the core; CLAP and VST3 (`vst3` 0.3.0, MIT/Apache; no GPL `vst3-sys`) |
| `nice-plug-egui` | `=0.6.0` | egui 0.37.0, egui-baseview 0.9.0, baseview 0.4.1 |
| `nice-plug-xtask` | `=0.1.1` | the bundler used by `cargo xtask bundle` |

Keep `crates/plugin` thin: no product logic, just mapping host params, notes, state and the editor onto `enth-session` and `enth-ui`.

Switch to **clack + clap-wrapper** if, within two days of trying, the Phase 0 shell spike can't achieve any of these must-haves: (a) 72 fixed host params with stable IDs, (c) persisting an arbitrary patch blob with the project, (e) VST3 export, (f) passing `clap-validator`, (g) building on stable Rust. Slot renaming (b) and poly-mod (d) failing are recorded but don't force a switch.

**Outcome (2026-10-19):** (a), (c), (e), (f) and (g) passed on the first build, so the switch rule did not trigger. Details and numbers are in [docs/spikes/shell.md](../spikes/shell.md).

## Findings from the shell spike

- **(a), (c), (e), (f), (g) pass.** In native REAPER 7.82, headless: 72 params with stable ids (REAPER adds Bypass/Wet/Delta, so it reports 75), automation, a project save and reload in a new process restoring values, envelopes and the patch blob, CLAP and VST3. Also in Carla 2.5.8 (VST3). `clap-validator` 0.4.1: 36 passed, 0 failed, 8 skipped. Steinberg's VST3 validator (SDK 3.8.1): 537 of 537. Stable Rust 1.99.1, no nightly features. `cargo xtask reaper-test` repeats the REAPER checks as a local gate.
- **(b) Renaming works for CLAP with a small nice-plug patch; VST3 in REAPER can't.** Stock nice-plug 0.4.2 fixes parameter names at construction. A 13-file, +123/−4-line additive patch (a display-name override plus a main-thread CLAP `rescan(INFO)` and a VST3 `restartComponent(kParamTitlesChanged)`) makes REAPER show the new CLAP name in 50 ms. REAPER 7.82 rejects the VST3 title-change request, so VST3 in REAPER shows "Slot N" whatever we do. Carla's VST3 host does follow it. A lane that already exists keeps its old label but stays bound by id. The patch is not in the repo (it lives in the researcher's scratch); the open decision is to carry it in a small fork (RustAudio's AI-contribution policy rules out upstreaming code written by agents) or to accept "Slot N". Names must be derived from the patch on the main thread, after slot assignment and after state load.
- **(d) Poly-mod is declared correctly but untested in a host.** Macros are modulatable per note id and the plugin exposes `voice-info`. REAPER has no poly-mod UI; Bitwig is the reference host and is on the owner checklist.
- **(h) Second host:** Carla 2.5.8 is VST3-only (CLAP support exists only on its unreleased main branch); Ardour is VST3-only. Bitwig is the only CLAP and poly-mod host on Linux. Partly done; see the spike doc.
- **Two nice-plug pitfalls to design around:**
  1. `execute_gui` tasks may run **inline inside `process()`** when `process()` is on the thread nice-plug treats as main (Steinberg's validator does this), and then `assert_process_allocs` aborts on any allocation. Don't schedule main-thread work from `process()`, and make any task it does schedule real-time safe.
  2. **`NiceEguiApp::editor_closed()` is never called.** Don't rely on it; detect a reopen in `build()`.
- **Further findings:**
  - `VoiceID::id_or_fallback` in nice-plug-core 0.4.2 ignores the host's voice id; read `VoiceID::id()` and make our own fallback.
  - `assert_process_allocs` is gated on `debug_assertions`, so it checks only debug builds.
  - A `#[persist]` field of type `String` holding JSON is escaped twice in the state; persist a typed value.
  - REAPER's offline render restarts (deactivates, reactivates, resets) CLAP plugins about 30 ms after it starts, dropping a held note. Real-time playback isn't affected. Host-driven render tests must not depend on one long note.
  - A VST3 parameter set from a script takes effect only after a process cycle, so a script must wait before reading or saving.
- **Licences:** the dependency tree needed `BSD-1-Clause` (nice-assert-no-alloc), `Ubuntu-font-1.0` (egui's default fonts, scoped to one crate) and two `BSL-1.0` exceptions for Windows-only crates; see the 2026-10-19 note in [ADR-0004](0004-licensing.md).

## Note — 2026-10-19 (P1b research): the vendored fork and the nice-plug pitfalls

Sources: the P1b research session (`_local/sessions/2026-10-19-p1b-plugin-editor/`, report 01 and the summary). The open fork decision of the G0 note is settled: **carry the fork, vendored privately.** This takes the default the coordinator gave the owner earlier, and no objection was raised.

**The fork**

- **Vendored in the repo behind `[patch.crates-io]`, not a git fork.** A public fork would expose the project name (the repo is private), CI would depend on Codeberg being up, and `deny.toml` would need `allow-git`. The layout is in [architecture.md](../architecture.md#vendored-crates-p1b). The crates come from the crates.io `.crate` files that `Cargo.lock` pinned, with a pristine-import commit and then one commit per patch.
- **Four patches** (a fifth, for a lost note-on, came from lane TH; see the lane FK note below):
  1. **Slot rename** (13 files, +123/−4): a display-name override, a main-thread CLAP `rescan(INFO)` and a VST3 `restartComponent(kParamTitlesChanged)`. It applies cleanly to the crates.io sources. VST3 in REAPER still shows "Slot N".
  2. **`editor_closed`** (+9, in nice-plug-egui): `Drop` for the editor's app wrapper calls it. Measured: 20 builds and 20 `editor_closed()` calls (stock: none). `EguiEditorState::is_open()` is also reliable (20 of 20 opens and closes seen from `process()`), so correctness never depended on the patch.
  3. **baseview's xkb leak** (+4/−1): `xkb_keymap_unref` after the state is created. The editor's leak falls from 77 to about 16 KB per open/close cycle. baseview `master` still lacks it (checked 2026-10-19), and no issue mentions it.
  4. **Keyboard focus only while typing** (egui-baseview and baseview): no `focus()` on every click, focus while a text field is edited, release afterwards. It lets Space reach REAPER's transport after a click on a knob ([ADR-0002](0002-ui-toolkit.md#note--2026-10-19-p1b-research-layout-as-data-stable-ids-keyboard-focus)).
- **Pins are unchanged:** nice-plug `=0.4.2`, nice-plug-egui `=0.6.0`, egui-baseview 0.9.0, baseview 0.4.1, egui 0.37.0. The vendored crates keep their versions, so the `=` pins still match; keep them through P1b. nice-plug-egui 0.7 is expected together with baseview PR #357, which rewrites the X11 event loop: re-import the pristine files and rebase the patch commits (the xkb fix may need re-deriving). Budget about a day, as above.
- **Licences and upstreaming.** The nice-plug crates declare ISC, but their crates.io packages contain no LICENSE file, so the text is copied from the Codeberg tag `v0.4.2`; baseview and egui-baseview are `MIT OR Apache-2.0` with both files present. RustAudio's AI policy rules out upstreaming code written by agents. The owner can file issues in their own words (the xkb leak with the valgrind trace, `editor_closed` never called, runtime parameter names, no dirty-marking) and write the one-line xkb PR personally. Upstream fixes then shrink the fork.
- **Caveat:** vendored path dependencies are not lint-capped. The vendored crates build without warnings on 1.99.1 today (cold build 1 min 53 s, 544 MB peak), and `cargo deny check licenses sources` passes. But a toolchain bump that surfaces a warning fails CI under `CARGO_BUILD_WARNINGS=deny`, while clippy's `-D warnings` and `cargo fmt --check` skip the vendored directory. Pin, and add a per-crate `allow` with a reason when it happens.

**Pitfalls, added to the two from the shell spike**

- **Never call `GuiContext::set_state` while processing.** nice-plug would then apply that state on the audio thread, where our persisted-field `set` would lock the session and compile a plan. Patches load through state on the host's main thread.
- **nice-plug never marks the project dirty.** It never calls CLAP `mark_dirty` and has no VST3 `setDirty`. A parameter change dirties the project implicitly, but an editor edit that changes only the patch blob may not. Check REAPER's save prompt after such an edit: `reaper-test` reads `IsProjectDirty`, and if it reads clean, a dirty-marking patch is the next fork candidate.
- **`SAMPLE_ACCURATE_AUTOMATION = true` is required.** With `false`, a plugin render at host block 4096 differed from the CLI render from the start of the block that holds an automation change. With `true`, 20 of 20 runs were bit-identical ([design.md §5](../design.md#5-determinism)).
- **A state load is not followed by `activate` or `reset`.** The plugin learns of it only through its persisted field's `set`, which runs on the host's main thread while audio may be running. Parameters load first, then fields in name order.
- **FTZ:** nice-plug sets it only behind its `unsafe_flush_denormals` feature, which we leave off. The engine does not depend on FTZ either way.
- **Open:** `MidiConfig::MidiCCs` (needed for the mod wheel and pitch bend) registers 2,080 hidden VST3 parameters. Decide it before the first build leaves the machine. The editor's size and zoom are not persisted, because `EguiEditorState` has no setter.

## Note — 2026-10-19 (P1b lane FK): the fork as built, and what it measured

`vendor/` holds the five crates (nice-plug 0.4.2, nice-plug-core 0.4.2, nice-plug-egui 0.6.0, baseview 0.4.1, egui-baseview 0.9.0) with the sha256 of each `.crate`, and `vendor/check-pristine.sh` diffs the tree against the packages. The history is a pristine-import commit, the ISC licence files, a lint cap, the `[patch.crates-io]` block, five patch commits and the test harnesses (`vendor/tests/`, described in `vendor/README.md`). Everything below ran on this machine under Xvfb (Mesa llvmpipe, no real display) with the load average at 15 to 25 and 16 GB of swap in use, so the PSS numbers are noisy and are given as ranges. Not run: REAPER, a real display, Windows, macOS.

**A fifth patch.** Lane TH found that with `SAMPLE_ACCURATE_AUTOMATION = true` a note-on listed before a parameter change on the same frame is lost (spike-shell, 1024 events in a block, notes first: 337 of 346 notes never started). Cause, in the CLAP wrapper's `handle_in_events_until`: while it looks for the event that splits the buffer it queues every event it passes. A note, MIDI or polyphonic-modulation event on the splitting frame that the host listed *before* the splitting parameter or transport event was queued with a timing equal to the length of the slice, one past its last frame. The plugin's `next_event` loop (`timing <= sample`) never reaches it, and the queue is cleared for the next slice. VST3 sorts parameter changes before notes, so it never saw this. The fix finds the splitting event first and handles only the events before the first event of that frame, so the whole frame starts the next slice at timing 0 in either order. Proof with `enth-test-host bursts --order both --capacity 1024`: before the patch `applied_all_up_to_events` was 64 for notes-first (16 and 256 at block sizes 16 and 480) and 4096 for params-first, exit 1; after it, 4096 in both orders and identical peaks and `NOTE_END` counts at every count and at blocks 16, 64 and 480, exit 0. Controls: the same command on the build without the patch, and the host's own `--inject drop-after=64`, both exit 1. This is a nice-plug bug, small (one file, +51/−9), and the owner may report it. It also means the "`SAMPLE_ACCURATE_AUTOMATION = true` is required" pitfall above needs this patch to be safe with dense input.

## Note — 2026-10-19 (P1b F1b review): no `request_callback` patch; a rate-limited background pump instead

Sources: [session.md](../session.md#plan-delivery-and-who-drains-the-return-ring) (F1b review decision 1), checked against the vendored nice-plug 0.4.2 sources. Lane FK's note above does not cover this; it adds no patch.

**The question.** The session sends a plan only from its own entries (an edit, undo, redo, a state save or load, `activate`, the editor's frame). If a compile is still pending when nobody calls the session (two plans in flight because the host had stopped calling `process()`, and then the editor closed or went idle; or a host load arrived), the engine keeps playing an older plan until the next entry. Something has to wake a thread that may lock the session. The alternative named in the review was a fork patch that exposes CLAP `request_callback` as a plain "call me on the main thread", without nice-plug's inline execution; it would be real-time clean for CLAP only.

**The decision: no fork patch.**

- nice-plug's `execute_background` already does the job. In the CLAP and VST3 wrappers `ProcessContext::execute_background` is `schedule_background`: a bounded `try_send` to nice-plug's `bg-worker` thread, which never runs the task inline. (`execute_gui` is `schedule_gui`: when the calling thread is the one nice-plug treats as main it runs the task inline, and otherwise it queues the task and calls the host's `request_callback`.)
- The shell keeps an atomic "pump wanted" flag and sets it, after unlocking, whenever `status().compile_pending`. While the flag is set, `process()` clears it at most once per 50 ms of audio and calls `execute_background` with a pump task. The task locks the session, calls `Session::pump` and sets the flag again if a compile is still pending. nice-plug's documentation warns that duplicate scheduled tasks pile up; the flag and the rate limit prevent it.
- Cost on the audio thread: one bounded crossbeam `try_send` (it wakes the parked worker, which takes crossbeam's internal lock briefly, so the nightly RTSan run will see it), only while a compile is pending and never in steady state. The task itself runs on the worker, which may allocate and lock.

**What stays banned.** `execute_gui` from `process()`, for the reason in pitfall 1 above: it is `request_callback` underneath, but it runs inline when the host calls `process()` on the main thread (Steinberg's validator does). The one thing `process()` may schedule is the pump. [AGENTS.md](../../AGENTS.md#plugin-shell-nice-plug) carries the rule.

**Revisit if** the RTSan run flags the `try_send`, or a host starves nice-plug's worker thread. The patch that exposes `request_callback` is then the clean alternative for CLAP (VST3 would still need the worker). It is not built, so the fork keeps its five patches.

## Note — 2026-10-20 (P1b lane FK2): patches 6 to 9, and the offline-render flake

Four more fork patches (one commit each; `vendor/README.md` lists them with sizes and proofs). Everything below ran on this machine: REAPER 7.82 headless under Xvfb, clap-validator 0.4.1, Steinberg's VST3 validator (the Phase 0 build of SDK 3.8.1), load 4 to 11. Not run: a real display, Windows, macOS, Bitwig. Upstream nice-plug `main` is still `7197104c0d` (2026-10-18; checked 2026-10-20) and has none of them.

**Patch 6: dirty marking.** Lane RH measured that REAPER keeps the project clean after an editor-only edit. The fork adds `HostRequests`, a handle the wrapper gives the plugin once after construction (`Plugin::host_requests`), with `mark_dirty()`: CLAP `clap_host_state.mark_dirty()`, VST3 `IComponentHandler2::setDirty(true)`, both performed on the host's main thread (at once there, queued otherwise; one queued request absorbs the next). The shell calls it on the session's `ShellRequest::PatchEdited` (editor edits, undo, redo; host loads and folds push none). `reaper-test`'s `dirty-flag` is now a hard check: `IsProjectDirty` is 1 at once and 3 s after the edit on CLAP and VST3, and 0 with the editor open and no edit; the 15e197c bundle fails it (0 and 0). This supersedes the pitfall "nice-plug never marks the project dirty" above. Not covered: an editor preset load (there is none yet: when the editor gets one, the session should push `PatchEdited` from it) and the monitor bypass and editor preferences in the `enth` field (the session pushes `MonitorBypass` on host loads too, so the shell cannot tell a user's switch from a load).

**Patch 7: the VST3 MIDI CC parameters.** nice-plug already flags the 2,080 IMidiMapping parameters read-only and hidden (`kIsHidden`); REAPER lists them anyway (2,155 with enth's 72 and its own three) and reports each as not automatable, so it reads the flags but does not drop hidden parameters from its list. Whether its menus show them is for owner build 1. `Vst3Plugin::VST3_MIDI_CONTROLLERS` lets a plugin list the controllers it reads; enth lists CC 1, the one `notes::engine_event` takes (a test keeps the two in step), so REAPER lists 91 (16 on top of 75), the ids of the mapped parameters are unchanged, the mod wheel plays in both formats (the new `mod-wheel` scenario: level 0.403 to 0.000) and `cli-equal`'s `mod-controls` stays equal. Add pitch bend (129) to the list with the engine input. Hiding them from VST3 altogether would have cost the VST3 mod wheel.

**Patch 8: the rescan request on the main thread.** The question was whether PL's path (the shell sets the names during the load and `process()` asks for the rescan) is already safe for every host thread model. It is not, from the source: the process context's `request_param_info_rescan()` calls `schedule_gui`, which in the CLAP wrapper runs the task at once when `is_main_thread()` is true (`wrapper.rs`, `impl EventLoop for Wrapper`: the host's `clap.thread-check` when it offers one, else the thread that created the instance), and CLAP's thread model lets a host make its main thread the audio thread (`include/clap/ext/thread-check.h` on free-audio/clap `main`, read 2026-10-20: "The host may mark any OS thread, including the main-thread as the audio-thread"); an offline render may. Then `clap_host_params.rescan()` is called from inside `clap_plugin.process()`, which no host expects. In the VST3 wrapper on Linux it was worse the other way: with the editor closed, a request from the audio thread is not the main thread, so `LinuxEventLoop::schedule_gui` hands it to nice-plug's background thread, and `restartComponent` ran there, off the UI thread. `HostRequests::request_param_info_rescan()` is called from the shell's `settle` on the thread that renamed: the host's main thread during a state load, where it runs there and then (as nice-plug's own `rescan(VALUES)` does after a load, through `Task::StateChanged` from `set_state_inner`), or the GUI thread for an editor rename (queued). `process()` no longer asks; the in-process host's fake process context panics if it does. design.md §4's deviation note is gone.

**Patch 9, and the `clap/macro-automation` flake.** PL saw `macro-1-gets-louder` read 0.3694 instead of about 0.408 in 1 of 5 runs, with the plugin's inputs traced identical. 0.3694 is exactly note 14's level: the late median (notes 14, 16, 18) fell to it because note 16 or 18 was cut. Ten CLAP renders of the same project at low load all differed (md5): notes 0 to 23 were identical, note 24 (3.0 s) ranged from 0.0 to 0.414, sometimes note 25 instead, and everything after the cut differed slightly; six VST3 renders were sample-identical. A traced plugin showed why: REAPER activates the plugin in real-time mode when it opens the project, pre-rolls, resets twice and starts the render; about 30 ms of wall-clock time into the render it deactivated the plugin (at engine frame 123,392, 2.57 s of audio) and reactivated it in offline mode, and a fresh engine continued the render, so the note sounding there was lost and the next one too. The restart is nice-plug's: `ext_render_set` calls `request_restart()` when the host switches an active plugin to offline rendering, so that `activate` sees the new mode, and REAPER honours it whenever its main thread gets to it, mid-render. The cut's audio time is that wall-clock delay times the render's speed: about 3 s for a release build at low load, 2.2 to 3.9 s for a debug build (2 of 8 debug runs failed), around 2 s for PL's loaded machine. Not the rescan: with patch 8 alone the debug bundle still failed 2 of 8. This is also the "REAPER deactivates, reactivates and resets CLAP plugins about 30 ms into an offline render and drops held notes" of the shell spike and AGENTS.md: it came from nice-plug, it was 30 ms of wall time, not of audio, and it cut a note in every CLAP bounce of enth in REAPER that outlasted that delay, not only held notes.

`ClapPlugin::CLAP_RESTART_ON_RENDER_MODE_CHANGE` (default `true`, upstream's behaviour) lets a plugin opt out; enth does, because its engine renders the same in both modes. Traced with it: one activation and one continuous render. Debug bundle: 8 of 8 passed, 6 sample-identical to the first and 2 differing only in the first 1,375 samples (the first note's start after REAPER's pre-roll; never measured). The harness now renders the `macro-automation` project twice and requires the same audio from 0.25 s on (`render-repeatable`, both formats), which the 15e197c bundle fails on CLAP in 2 of 2 runs; 5 consecutive full `reaper-test` runs passed with 239 checks each and the late level at 0.4078 every time. The cost: in a CLAP host that switches an active plugin to offline rendering, the session's `Activation::offline` stays false, so the editor's audition notes are not refused during that bounce (before the patch they were not refused for its first 2 to 3 s either). VST3 is unchanged (REAPER sets `kOffline` before activating). If the refusal matters, a later fork patch can expose the current mode to the plugin without a restart.

**Owner build 1** (the real display, in REAPER): the save prompt after an editor-only edit (CLAP and VST3: REAPER should now ask), whether REAPER's FX parameter menus show the 16 hidden `MIDI Ch. N CC 1` parameters, the mod wheel from a hardware controller on both formats, and a CLAP offline bounce of a run of short notes (no note should drop about a second or two in).

**Candidates for the owner's own upstream issues:** the restart on a render-mode change (REAPER honours it mid-render and a note drops in every CLAP bounce), no dirty marking, the 2,080 MIDI CC parameters hosts list despite `kIsHidden`, and `getParameterInfo` accepting an index equal to the count.

## Consequences

- Fastest path to a working CLAP/VST3 synth with an egui editor in REAPER. The spike's shell is about 800 lines for 72 params, poly-mod ids, state and an 8-voice synth, and incremental rebuilds take 1–7 s.
- We inherit a young framework's churn and a single maintainer; pinning, a committed lockfile and a thin shell limit the blast radius. nice-plug-egui 0.7 is expected to move to a host timer API (baseview #357); budget about a day.
- Slots show generic names ("Slot 7") in VST3, and in CLAP unless we carry the rename patch; that is acceptable for v1.
- Tests that drive a real host stay local (`cargo xtask reaper-test`); CI runs `clap-validator` on the bundle.

## Alternatives considered

- **clack + own glue** — most control and full CLAP coverage; costs weeks of plumbing before the first sound. Kept as the escape hatch, and used anyway for `tools/test-host` (clack-host). The researcher's probe (clack 0.2.0's own polysynth example plus clap-wrapper 0.3.1 for VST3): builds in 30 s with 12 crates, but fails 3 clap-validator state tests, and the crates.io wrapper bundles clap-wrapper 0.14.0, which lacks the 0.16.0 fix for stale VST3 parameters after a state load (REAPER showed the default after a reload). The estimate for reaching parity on our narrow needs is 2–4 weeks.
- **Raw clap-sys** (as in NovoNotes' WRAC template) — even lower level; no benefit over clack for us.
- **Original nih-plug** — maintenance mode; VST3 export via the GPLv3 `vst3-sys` crate.

## How we'd know we're wrong

Any must-have in the Phase 0 shell table fails, or framework churn costs more than a day per month after S1 (Instrument 0.1). Also: the editor misbehaving on the real display (blank first open, wrong scale, lost keyboard focus) in a way we can't fix in a day, or the single maintainer leaving.
