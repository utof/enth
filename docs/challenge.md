# Challenges, codes and scoring interfaces

`enth-challenge` (L4) holds what a Recreate round is made of: the `Challenge`, the randomizer's `RandomSpec`, the phrases, the challenge codes, the scorer interfaces and the round's results. This page is the reference for its persisted types and interfaces, and what the F1r judge reviews ([phase-2.md](phase-2.md#freezes)). The designs behind it are [design.md §6](design.md#6-challenge-and-scoring) and [§9](design.md#9-randomizer-and-difficulty), [ADR-0007's 2026-10-20 note](adr/0007-metric-v1.md#note--2026-10-20-r1s1-research-five-fixes-for-the-sound-score) and reports 01 and 02 of the [R1/S1 research](../_local/sessions/2026-10-20-r1-s1-recreate-and-instrument/summary.md).

## How a round uses these types

1. The player picks settings (or pastes a code). The shell draws a fresh seed and keeps 40 bits of it, so the code stays short.
2. `ChallengeCode::decode(text)` gives the code; `code.spec()` gives the `RandomSpec`.
3. `prepare_round(&spec)` ([Scoring a round](#scoring-a-round)) regenerates the target (lane RG: the patch, the phrase id it picked, the parameters it randomized and the target's **fingerprint**), builds `Challenge::recreate(spec, phrase)` and prepares every scorer the challenge names.
4. `code.verify(&round.fingerprint(), EngineVersion::CURRENT)` checks the target. A long code with another fingerprint prefix is refused; another engine version gives a warning.
5. `score_round(&round, &patch)` scores each submit: sound, structure and combined from the challenge's scorers, and the pass from sound alone (`ScoreReport::new`).
6. The round ends with a `RoundResult` for the results drawer and the round log.

**The target patch is never persisted.** A round keeps the code text it started from, and regenerates the target from it. A long code made on another machine keeps that machine's engine version this way.

## Challenge v1

```json
{"schema":"enth.challenge/1",
 "target":{"kind":"seed","spec":{"generator":1,"seed":42,"difficulty":0,"amounts":[null,null,null,null,null,null],"musical":100,"template":0}},
 "answer":"patch","phrase":1,"start":{"kind":"template","template":0},"constraints":{},
 "assists":{"live_meter":false,"dim_unused":false,"hint_budget":null},
 "scoring":{"sound":"sound/1","structure":"structure/1","combined":"combined/1","time":"time/1","sound_weight":50,"pass_mark":90},
 "meta":{"title":"","tags":[]}}
```

| Field | Type | v1 meaning |
| --- | --- | --- |
| `schema` | `"enth.challenge/1"` | always first |
| `target` | `Target` | `{"kind":"seed","spec":RandomSpec}`: generated by the frozen generator the spec names. Patch, audio and expectation targets (lessons, "create from sound", text goals) are later variants |
| `answer` | `AnswerKind` | `"patch"`: the player's patch is the answer. Choice and value answers (ear training) come later |
| `phrase` | `PhraseId` (`u16`, ≥ 1) | an id in RG's phrase table. For a seed target it is the generator's pick for that spec |
| `start` | `Start` | `{"kind":"template","template":N}`: the template's start patch. For a seed target it must be the spec's own template (`start_mismatch`) |
| `constraints` | `Constraints` | `{}`. R1 locks nothing; a version that adds a constraint migrates v1 to "no constraint" |
| `assists` | `Assists` | `live_meter` (off: score on submit), `dim_unused`, `hint_budget` (`null` = no limit, 0 = none) |
| `scoring` | `ScoringSpec` | scorer ids, `sound_weight` (%), `pass_mark` (sound %) |
| `meta` | `ChallengeMeta` | `title`, `tags`; empty for a generated round |

Rules:

- **Versioned.** `Challenge::from_json` checks the schema (`missing_schema`, `bad_schema`, `challenge_too_new` for a newer one), then decodes and validates. Embedded in another serde type, a challenge goes through the same checks (`try_from`).
- **Unknown fields are refused**, at every level, and every change to the shape is a version bump with a migration. A field is never silently ignored, because ignoring a constraint would play a different game. (The outputs, a score report and a round result, are read tolerantly instead: [below](#scoring-interfaces).)
- **Integers only.** No float anywhere in a challenge.
- **Byte-deterministic.** `to_json` writes compact JSON in declaration order; the fixtures pin the bytes.
- `Challenge::validate` checks what the types cannot: a valid spec (a generator and a template this build has, a seed below 2⁵³), the start template, a non-zero phrase, percentages at most 100.

`ScoringSpec::recreate(difficulty)` is the Recreate default: this build's `RECREATE_SCORERS`, a sound weight of `50 + 30·difficulty/100` % (50 % at difficulty 0, where structure is unambiguous and ADR-0007 asks to lean on it; 80 % at 100), and the pass mark `DEFAULT_PASS_MARK` = 90. `ScoringSpec::with_scorers` gives the same weights with named scorers (the fixtures and the golden challenges pin the v1 ids that way). The weights live in the challenge, so a later default never changes an old challenge's score.

**The default scorers were stubs until SS and ST landed** (F1r review S12): `RECREATE_SCORERS` was `sound-stub/1`, `structure-stub/1`, `combined-stub/1`, `time/1`; lane ST switched structure and combined to `structure/1` and `combined/1` ([below](#structure-combined-and-time-lane-st)), and lane SS sound to `sound/1`, so it is now `sound/1`, `structure/1`, `combined/1`, `time/1`. The stubs score in parameter space under their own ids, so no stub score is ever stored, logged or pinned as `sound/1`. Each lane switched its entry in the commit that landed its scorer. **The pass mark stays and the curve moves:** SS fits `sound/1`'s curve so that the rating-4.5 point lands on 90, GR1's refit is `sound/2` with the same mark, and the stubs use 90 as is.

**The scored render** is fixed by two constants in `model`: `SCORING_SAMPLE_RATE` = 48,000 Hz and `SCORING_SEED` = `0x0E17_5EED`, written out (F1r review S12) so it can never follow the CLI's default silently; a test checks it equals `enth_render::DEFAULT_SEED`. So `enth render` of a target with its phrase gives exactly the audio the scorer hears and Target ▶ plays.

### Phrases

A `Phrase` is the notes and length a target is heard and scored through: `notes: &'static [PhraseNote]` (key, velocity 1–127, `start_ms`, `hold_ms`) and `length_ms`. Integers only, so a phrase is exact. `Phrase::performance()` turns it into a render `Performance` with velocity `v/127` and times `ms/1000`: plain IEEE divisions, the same on every platform. Phrases live in code, in RG's table, and are referred to by `PhraseId`; a released phrase never changes, and a different phrase is a new id. `Phrase::validate` is the check RG's table test runs.

## `RandomSpec`

```rust
pub struct RandomSpec {
    pub generator: u16,                // 1..=LATEST_GENERATOR
    pub seed: u64,                     // 0..=MAX_SEED (2^53 - 1); a short code holds 40 bits
    pub difficulty: u8,                // 0..=100: picks the level
    pub amounts: [Option<u8>; 6],      // 0..=100 per Category; None follows difficulty
    pub musical: u8,                   // 0..=100: 100 = priors only, 0 = uniform
    pub template: u8,                  // 0..=LATEST_TEMPLATE; 0 = the starter superset
}
```

JSON: `{"generator":1,"seed":42,"difficulty":25,"amounts":[null,null,null,null,null,null],"musical":100,"template":0}`, every number an unsigned integer (a float that goes through text and back can flip a draw). Unknown fields are refused. The spec has no version of its own: it is persisted only inside a versioned challenge or code, and a change to it bumps both. `Category` is `Oscillators, Filter, Envelopes, Modulation, Effects, Structure`, in difficulty order, and indexes `amounts`.

`RandomSpec::validate` is the one check: a generator from 1 (`no_generator`) to `LATEST_GENERATOR` (`code_too_new`), a template up to `LATEST_TEMPLATE` (0 today; `code_too_new`: template ids are append-only, so an unknown one is a newer build's), a seed up to `MAX_SEED` = 2⁵³ − 1 (`out_of_range`: the JSON form writes the seed as a number, and JavaScript and many JSON tools keep only 53 bits of one, which would silently give another target; the long code's 64-bit field stays), and every percentage at most 100 (`out_of_range`).

**What RG follows** (RG settles the rest at F1r):

- The generator calls `validate()` first and refuses a spec that fails it; it never clamps.
- It implements every version from 1 to `spec::LATEST_GENERATOR` (1 today). Freezing a new version bumps that constant in the same commit that adds the version's golden. Likewise every template from 0 to `spec::LATEST_TEMPLATE`.
- **The start patch has no slot assignments and routes no macro or mod wheel, and no target adds such a route** (lane SG's host-automation rule: host automation must not reach a round's patch; F1r review N3). `random::tests::the_start_has_no_slots_and_no_macro_routes_and_targets_add_none` checks it.
- Levels: the presets put levels 1–5 at difficulty 0, 25, 50, 75 and 100. Any banding that keeps those five in different levels, in order, works; the proposal is 0–20, 21–40, 41–60, 61–80 and 81–100.
- Template ids are append-only, like preset and phrase ids.
- A seed made by a formula rather than drawn (a daily challenge's, say) keeps its top 40 bits (`>> 24`), so its code stays short.
- Generation returns the target patch, the phrase id it picked, the randomized addresses (observable, in address order), because the scorers' `TargetContext` takes all three, and the target's [fingerprint](#the-target-fingerprint).

### Presets

A short code carries settings by preset id (`SpecPreset`). Code v1's table is frozen; new presets (archetypes, a "chaos" level) are appended with new ids.

| Id | Name | `difficulty` | `amounts` | `musical` | `template` |
| --- | --- | --- | --- | --- | --- |
| 1 | Level 1 | 0 | all `None` | 100 | 0 |
| 2 | Level 2 | 25 | all `None` | 100 | 0 |
| 3 | Level 3 | 50 | all `None` | 100 | 0 |
| 4 | Level 4 | 75 | all `None` | 100 | 0 |
| 5 | Level 5 | 100 | all `None` | 100 | 0 |

## Codes v1

A challenge code is a `RandomSpec` that a person can read out, type and paste: a versioned bit string in [Crockford base32](https://www.crockford.com/base32.html) with a weighted check symbol over GF(32), itself one of the 32 data symbols. `ChallengeCode` is the type; serde reads and writes its canonical text.

| Form | Symbols (hyphens not counted) | Carries | Starts with | Example |
| --- | --- | --- | --- | --- |
| **short** | 13 data + 1 check = **14** | a preset id, the generator (< 4096), the seed (< 2⁴⁰) | `1` | `1080-1000-0001-AB` (level 2, seed 42) |
| **long** | 34–43 data + 1 check = **35–44** | the whole spec, the engine version, a 32-bit target-fingerprint prefix | `H` | `H000-G07Z-ZZZZ-ZZZZ-ZA4C-07ZZ-ZZG2-8XBS-N5J0-0A` |

Every symbol is a data symbol (F1r review S2): Crockford's mod-37 check, which code v1 first had, put one of `* ~ $ = U` at the end of about one code in seven, which is hard to read aloud and breaks in Markdown, URLs and shells. Code v1 was re-frozen with the GF(32) check before any code was shared. `ChallengeCode::short(spec)` gives the short form when the spec is a preset's with a short seed and generator; otherwise `ChallengeCode::long(spec, engine, target_prefix)`. `Challenge::code(prefix)` picks for you.

### Layout

Fields are written most significant bit first and cut into 5-bit symbols; the last symbol is zero-padded. The first symbol is `form << 4 | version`, so every later version can be told apart before its layout is known. **Version 15 is reserved as an escape** (`CODE_VERSION_ESCAPE`, F1r review N2): a later kind of code (R5's result codes, duels) starts with it in either form and puts a kind field next, so the 1-bit form never runs out; versions 2–14 are for new layouts of the two forms, and this build reads any of them as `code_too_new`.

| Short (65 bits) | Bits |
| --- | --- |
| form = 0 | 1 |
| version = 1 | 4 |
| preset id | 8 |
| generator | 12 |
| seed | 40 |

| Long (169 + 7k bits; k = set amounts) | Bits |
| --- | --- |
| form = 1 | 1 |
| version = 1 | 4 |
| generator | 16 |
| seed | 64 |
| difficulty | 7 |
| musical | 7 |
| template | 8 |
| engine major, minor, patch | 8 + 8 + 8 |
| target-fingerprint prefix | 32 |
| amounts mask (`Category::ALL` order, first category in the high bit) | 6 |
| each set amount, in that order | 7 each |

The prefix is the first 32 bits of the regenerated target's [fingerprint](#the-target-fingerprint), big-endian (`TargetPrefix`, shown as the fingerprint's first 8 hex digits). It is not a patch hash: `canonical_hash` holds the patch schema, so the first schema bump would have refused every long code.

### The bit budget (open check, settled here)

The summary asked for about 13 characters carrying the generator and engine versions and a 32-bit prefix; 13 symbols hold 65 bits, which cannot hold all of that. So:

- **The short code holds 64 bits of payload** (version, preset, generator, seed) plus the form bit, in 13 symbols and a check: report 01's form. It carries **no prefix and no engine version.** Its guarantee is that a generator version is frozen and pinned by its spec → fingerprint golden on Linux, Windows and wasm (macOS weekly). A short code names only preset settings, which are exactly what those goldens cover. Two typos can give another valid short code: 1.3 % of random double substitutions with the GF(32) check (264 of 20,000, lane F1R's probe; the judge measured 0.9 % for the mod-37 check), accepted for R1 (F1r review S3). A round's log line carries the target's fingerprint and the engine version, so a replay of a logged code can still tell drift from a different target.
- **The long code carries both**: the engine version (24 bits, enough for `0.2.0`-style versions up to 255.255.255) and a 32-bit prefix (a drifted target slips through with probability 2⁻³²). It is the form for custom settings. R5's result codes take the escape version: they carry the answer's fingerprint and the scores (a patch is kilobytes, so never the patch itself).

### Reading a code

- Case is ignored; `O` reads as `0` and `I`/`L` as `1` (Crockford's aliases); hyphens and whitespace are ignored anywhere. `U` and `* ~ $ =` are no symbols at all (`bad_symbol`).
- Checks, in order: every character is a symbol (`bad_symbol`); 2 to 64 symbols (`bad_length`; `empty_code` for none); the check symbol (`bad_check`); the version (`code_too_new` from 2 to 15, `bad_field` for 0); the form's exact length (`bad_length`); zero padding and preset 0 (`bad_field`); a preset this build does not have (`code_too_new`: preset ids are append-only, so it is a newer build's, never damage); the spec (`RandomSpec::validate`: `out_of_range` for a percentage or a seed from 2⁵³, `no_generator`, and `code_too_new` for a generator or template this build does not have).
- `decode` never panics; a property test feeds it arbitrary text.

**What the check symbol catches.** Read every symbol as an element of GF(32) = GF(2)[x]/(x⁵ + x² + 1), whose α = x has order 31 (the polynomial is primitive). The check c makes the whole word s₀ … sₙ₋₁ c vanish at α: Σⱼ wⱼ·sⱼ = 0 with the weight α^j for the symbol j places from the end (the check has weight 1). So c = α · (the data read as a polynomial at α), one Horner pass with a shift and an XOR per symbol. Addition is XOR, so a difference is a sum:

- **Every single substitution.** Changing a symbol a to b ≠ a at j places from the end changes the sum by α^j·(a + b), and neither factor is 0. That holds for the check symbol too (j = 0).
- **Every adjacent swap.** Swapping a ≠ b at places j + 1 and j changes the sum by α^j·(1 + α)·(a + b): α ≠ 1, so no factor is 0. That includes the last data symbol and the check (j = 0), at any length.
- **A dropped or added symbol** in a short code, by its fixed length. In a long code the length follows the amounts mask, so the check catches it with probability 31/32.

The property tests check the first two exhaustively for every position of 256 random codes per run, and `alpha_is_primitive` checks α's order.

### Versions and the engine

| Mismatch | What happens | Why |
| --- | --- | --- |
| Code version newer than this build's | refused, `code_too_new` | the layout is unknown |
| Generator newer than `LATEST_GENERATOR` | refused, `code_too_new` | this build cannot regenerate the target |
| Long code's fingerprint prefix ≠ the regenerated target's | refused, `target_mismatch` | the round must never be scored against a different target; it means a generator was not frozen, a bug to report |
| Long code's engine version ≠ this build's | **warning only**, `engine_differs` (`CodeWarning`) | the target patch is the same; only its audio, and so the scores, may differ slightly |

`ChallengeCode::verify(&fingerprint, EngineVersion::CURRENT)` does the last two; a short code passes it (it carries neither). Warning on another engine is right for solo R1; comparing two players' scores across engine versions is R5's concern, and R5 must refuse or rescore on a mismatch (its result codes carry the engine version; F1r review N2).

## Generator versions are frozen

- **A generator version's output never changes.** Version N gives the same target fingerprint for the same spec, on every platform, forever. Any change to the priors, the rules, the mask, the minimum step, the quantization or the draw order is a new version, frozen beside the old ones; old versions are never edited or removed.
- **What is enforced** (F1r review M2, rewritten from the first draft's "each version emits a patch in its own schema", which nothing built): a version runs on its template's frozen start patch (template 0's bytes are pinned), migrated to the current schema when it loads, and reads the live catalogue (`ParamSpec`s, through `Patch::spec`) for its draws, quantization and just-noticeable steps. So **a version reads only catalogue fields that a test pins**: `random::tests::the_catalogue_fields_v1_reads_are_pinned` snapshots the range, scale, unit, default, items, key and flags of every parameter v1 reads (each address in `priors::v1::SLOTS`, every route destination v1 can draw, and `master.level`) in `src/random/catalogue-v1.txt`. A catalogue change that trips it must keep v1's old values in a frozen copy that v1 reads, or ship generator v2; it never updates the snapshot. A catalogue change v1 does not read (a new parameter, a new module, a schema bump that renames none of v1's keys) changes no v1 target and no fingerprint.
- **Goldens store spec → target fingerprint per version**: 1,000 (seed, settings) pairs → the [fingerprint](#the-target-fingerprint), in `enth-golden`, on Linux, Windows and wasm on every push and on macOS weekly (RG writes them; GC adds the challenge goldens). A patch hash would move with the schema; the fingerprint moves only with the target. A golden of a released version never changes; a new version adds its own file.
- **Releasing a version** bumps `spec::LATEST_GENERATOR` in the same commit as its golden. New rounds use the latest version; old codes keep theirs.
- The same holds for the other tables a code depends on: preset ids, phrase ids and template ids are append-only, and a released entry never changes.

## The target fingerprint

`TargetFingerprint` (`enth_challenge::fingerprint`, F1r review M1) is a target's identity, independent of the patch schema: what a long code's prefix, a round saved mid-play (`target_hash`), the round log and generator goldens check. `random::Generated::fingerprint` holds it, and `PreparedRound::fingerprint` passes it on.

It is SHA-256 of a frozen byte string: the magic `enth-target-v1`, the generator (u16, big-endian), the phrase id (u16), the entry count (u32), then each entry in byte order of its key: the key's length (u16) and UTF-8 text, a tag (`p` a parameter value, `r` a route depth, `e` an enable flag) and the value (an f32's bits, big-endian, -0.0 as 0.0; or one byte, 0 or 1). Keys are names, never positions: a parameter's address (`filter1.cutoff`, `master.level`), a route's `<source>-><destination>` and a module's `<id>.enabled`.

Generator v1's entries are every draw it made, at its value in the final patch, and `master.level` when its headroom rule lowered it. Nothing else of the patch enters it, so re-encoding the target (a schema bump's migration) or adding a catalogue parameter keeps every fingerprint (`random::tests::t1_*`), while any drawn value that moves by one ulp gives another. The encoding is frozen with its magic (`fingerprint::tests::the_v1_preimage_is_pinned`); a generator that needs another kind of entry uses a new magic.

## Scoring interfaces

Scorers are additive (design.md §6): each has a `ScorerId` written `name/version`. A change that would move any score is a new id beside the old one (metric v1.1 is its own id), so a stored report keeps meaning what it said.

| Id | What | Lane |
| --- | --- | --- |
| `sound-stub/1`, `structure-stub/1`, `combined-stub/1` | The stubs ([below](#scoring-a-round)): parameter space, no render; the default until SS and ST landed, still dispatched by id (the golden challenges' `stub` blocks, `skr-v1.txt`) | CT |
| `sound/1` | Metric v1 with report 02's fixes and **the fitted curve** (after metric session 2) | SS |
| `sound/2` | The same metric, the curve **refitted to GR1's blind ratings** (reserved); the pass mark stays 90 | SS, after GR1 |
| `structure/1`, `combined/1` | Structure % and w·sound + (1 − w)·structure | ST |
| `time/1` | The first passing submit in editor-visible time: a rule the session keeps, not a scorer to run | SG |

```rust
pub trait Scorer: Send + Sync {
    type Prepared: Send + Sync;                       // per-challenge state: renders, floor, JND scale
    type Score: Clone + Debug + Send + Sync;          // SoundScore or StructureScore
    fn id(&self) -> ScorerId;
    fn prepare(&self, target: &TargetContext<'_>) -> Result<Self::Prepared, ScoreError>;
    fn score(&self, prepared: &Self::Prepared, answer: &Patch) -> Result<Self::Score, ScoreError>;
}

pub trait Combiner: Send + Sync {
    fn id(&self) -> ScorerId;
    fn combine(&self, scoring: &ScoringSpec, sound: &SoundScore, structure: &StructureScore) -> Combined;
}

pub struct TargetContext<'a> {
    pub challenge: &'a Challenge, pub target: &'a Patch, pub start: &'a Patch,
    pub phrase: &'a Phrase, pub randomized: &'a [ParamAddr],
}
```

- **Pure.** No I/O, threads or clocks. `prepare` runs once per challenge (about 0.1–1 s of renders), `score` per submit; the shell's worker runs both, off the UI and audio threads. The session never needs the traits, only their results.
- **Deterministic.** A score that decides pass gives the same bits on every platform: the scalar FFT path, the in-house `libm` loudness, a fixed summation order (SS).
- **Only sound decides pass:** `ScoringSpec::passes(sound %)` is `sound % ≥ pass_mark`. The pass mark is an integer sound %; SS fits the curve so that the rating-4.5 point lands on it.
- **Reports are read tolerantly** (F1r review S6): every output type (`SoundScore`, `Component`, `StructureScore`, `ParamScore`, `ModuleTerm`, `Combined`, `ScoreReport`, `RoundResult`) ignores unknown fields, gives a field added later a default when it is missing, and reads an unknown enum value as `unknown` (`ComponentKind`, `Direction`, `Closeness`, `Verdict`, `ModuleStatus`, `Outcome`, `Agreement`). So a lane adds an output field within `enth.score-report/1` (optional, with a default), and a newer build's report still reads. The challenge and the spec stay strict.

| Type | Holds |
| --- | --- |
| `SoundScore` | `scorer`, `percent` (0–100), `distance` (raw metric), `floor` (the target's nuisance floor), `scale` (per-challenge JND scale), `jnd` (= max(0, distance − floor) / scale), `components` |
| `Component` | `kind`, `direction` (`same`, `higher`, `lower`, `missing`, `extra`: the answer relative to the target), `closeness` (`close`, `a_bit`, `far`), optional `target` and `answer` readings in the kind's unit (never shown during a round) |
| `ComponentKind` | `pitch` (cents re A4), `brightness` (centroid, Hz), `harmonics` (harmonic content, the waveform: odd-to-all harmonic energy, 0–1), `attack` (ms), `envelope` (decay to sustain, ms), `sustain` (sustain level, dB re the peak), `release` (ms), `noisiness` (noise ratio), `movement` (rate of beating, tremolo or sweep, Hz). Level 1 is waveform plus octave, so harmonics and the sustain level have rows of their own (F1r review S6) |
| `StructureScore` | `scorer`, `percent` (over the randomized parameters), `params` (one `ParamScore` per randomized parameter, then one per parameter the player moved that the target did not randomize, each part in address order), `modules` (`ModuleTerm`s the matching left over) |
| `ParamScore` | `addr` (the target's, text, so an old report reads after a catalogue change; `param_addr()` parses it), `answer_addr` (the matched address in the player's patch, where the ring goes once modules are added and removed; `None` when the player has no match), `score` (0–1), `verdict` (`good`, `near`, `bad`: the ring), `direction` (`same`, `higher`, `lower`, `missing`), `randomized` (false for a "moved but not randomized" row, never counted in structure %) |
| `ModuleTerm` | `id`, `kind`, `status` (`missing` or `extra`) |
| `Combined` | `scorer`, `percent`, `sound_weight` |
| `ScoreReport` | `sound`, `structure`, `combined`, `pass_mark`, `passed`, `engine` (the engine that rendered the scored audio: an engine change can move a sound score); `margin()` = sound % − pass mark; `verdicts()` for the rings (randomized rows); `check_against(&scoring)` (the ids, the pass mark, the percentages and the pass recomputed: what the session checks before it records a worker's report) |
| `ScoreError` | `render_failed`, `analysis_failed`, `unscorable`, `unknown_scorer` |

`ScoreReport` is JSON with `"schema": "enth.score-report/1"` first. Reading one refuses a percentage outside 0–100 or not finite, and a `passed` that disagrees with the sound % and the pass mark. Scores are `f64`, written with shortest round-trip text, so the golden challenges can pin them to 1e-6.

## Scoring a round

`enth_challenge::score::round` (F1r review S5) is the round's composition as one pure function, so no shell composes scorers: the plugin's game worker, the CLI's `enth compare` and the golden challenges call the same code.

| Function | Does |
| --- | --- |
| `prepare_round(&spec) -> Result<PreparedRound, RoundError>` | Validates the spec, regenerates the target from its template's start, **refuses a silent target** (`silent_target`: its scored render reads no loudness, at or below −70 LUFS, so any silent answer would score 100 %; R1/S1 lane INT), builds `Challenge::recreate(spec, phrase)` with this build's default scorers, prepares each |
| `prepare_challenge(challenge)` | The same for a given challenge (a golden challenge, `compare --challenge`, a file): validates it, regenerates its target, refuses another phrase than the generator's pick (`phrase_mismatch`), prepares the scorers it names; a silent target is scored as given (the golden `silent-l2-s23` pins it) |
| `target_lufs(&target, phrase)` | The target's loudness as `sound/1` measures it before its gain (`None` when silent): the check `prepare_round` makes |
| `score_round(&round, &patch) -> Result<ScoreReport, ScoreError>` | Sound, structure, combined and the pass from sound alone; refuses a scorer that answers under another id |
| `score_structure(&round, &patch)` | The structure score alone: the live rings, no render |

`PreparedRound` is `Send + Sync` and built only by these functions, so its parts belong together: `challenge()`, `start()`, `target()`, `generated()`, `params()` (the randomized parameters), `fingerprint()` and `phrase()`. A worker keeps it per round (or shares it in an `Arc`).

**The dispatch.** Each id a challenge names maps to an implementation: the stubs first, then each lane's hook **in its own file**, so a lane adds its scorer without editing CT's: `score::sound::prepare(id, ctx)` (SS), `score::structure::prepare(id, ctx)` and `score::combined::combiner(id)` (ST); each returns `None` for an id it does not have. `time/1` is the only time rule. Anything else is refused, `unknown_scorer` (until SS lands it, `sound/1` too: a challenge is never silently stubbed). A hook wraps its scorer with `Ready::prepare(scorer, ctx)`, which keeps the scorer and its `prepare` output behind the `PreparedScorer` trait.

**The stubs** (`score::stub`, CT): every one works in parameter space, with no render, through generator v1's just-noticeable steps (`priors::jnd`, `Jnd::steps`). A randomized parameter scores 1 within one step of the target, falling linearly to 0 at four, with the ring good under one step, near under three, bad beyond; sound % and structure % are both the mean over the randomized parameters, combined is w·sound + (1 − w)·structure, and the sound stub's components come from the parameters that feed each kind (osc semitones → pitch, the wave → harmonics, the filter → brightness, the envelopes → attack, envelope, sustain, release; noise → noisiness; LFOs → movement). The target scores 100. **Not a sound score**: it lets SKR, RUI and GC wire and test the round before SS and ST land.

**Module matching** (`score::matching`, owner ST, pre-declared by F1R): `match_modules(target, answer) -> ModuleMatching` pairs the player's modules with the target's (`answer_of`, `target_of`, `missing`, `extra`, `answer_addr`), for SS's mapping before the scoring render (ADR-0007 fix 2), ST's structure score and the rings. Lane ST filled it: [Module matching](#module-matching) (and `Matcher`, the round's pairing that SS and ST share).

### Levels and what each randomizes

`difficulty` picks the level: 0–20 → 1, 21–40 → 2, 41–60 → 3, 61–80 → 4, 81–100 → 5 (the presets sit at 0, 25, 50, 75 and 100). Each level adds categories; an unlocked category with `amounts = None` draws its default set:

| Level | Adds | Default set |
| --- | --- | --- |
| 1 | Oscillators | `osc1.wave`, `osc1.semi`, and `osc1.pw` when the wave is pulse (`position` when it is the wavetable). Once structure enables them: osc 2's wave, semi, fine, level (pw, position) and the noise's color and level |
| 2 | Filter | `filter1.mode`, `cutoff`, `resonance`; `keytrack` under the octave pair |
| 3 | Envelopes | env 1's attack, decay, sustain, release (one pluck / pad / keys archetype for all four); the route env 2 → `filter1.cutoff` and env 2's decay and sustain; `env1.velocity` under the octave pair |
| 4 | Modulation | An lfo 1 route (vibrato on `osc1.fine`, wah on the cutoff, tremolo on `osc1.level`, or PWM on a pulse) with its rate and shape; a second, on lfo 2, 35 % of the time |
| 5 | Effects, Structure | Effects: the reverb (60 %) and the compressor (30 %) switched on, with wet, decay, room and threshold, ratio. Structure: osc 2 (50 %) and the noise (30 %) switched on, the phrase (held 50 %, octave pair 30 %, legato pair 20 %), legato mode and glide under the legato pair, and a velocity → cutoff route under the octave pair |

`amounts[c] = Some(0)` switches a category off at any level; `Some(a)` switches it on and draws the first ⌈n·a/100⌉ entries of its full list (the default set first, then extras such as filter drive, env 2's attack and release, the reverb's high cut and the compressor's times), with continuous values pulled towards the start by `a/100`. These counts are "beta" for GR1: level 3 already draws 12–13 parameters where design.md §9 estimated 6–10, and GR1's pass rates calibrate it.

### Keyed draws and priors

- Every value comes from `derive(derive(seed, fnv1a64(key)), attempt)`. Keys are addresses (`filter1.cutoff`), `<id>.enabled` and `<src>->*` (a route's depth and destination). Shared choices (an envelope archetype, an LFO destination, the phrase) are drawn at attempt 0 from their own keys. Adding a parameter never moves another draw (P6), and a higher level keeps every lower draw and value (P3).
- With probability `musical` % (from `<key>/musical`) a value comes from its prior, otherwise uniformly over its observable range in its normalised scale. Above `musical` 20 that range is the safe one: resonance at most 80 %, semitones within ±24, the cutoff relative to the note.
- The priors are relative to the phrase's note through osc 1's transposition (f0 = C3 · 2^(semi/12)): LP cutoff log-uniform from 1.5 f0 to 12 kHz, band-pass f0 to 8 f0, high-pass f0/2 to 4 f0; resonance `60·u^1.5` %; octaves for osc 1 and intervals for osc 2; envelope times capped at the phrases' 1.5 s hold and tail; deterministic LFO shapes only (sample & hold and smooth random follow the render seed).
- Reachable values: continuous values to 3 significant digits, route depths in 5 % steps (never 0), discrete values exact.
- Headroom: when the enabled sources sum above 100 %, `master.level` (a gauge, never drawn) drops by their sum in 0.5 dB steps, at most 12 dB.

### The observability mask

`observable` gives every parameter, route and enable flag one `Visibility`. Only `Observable` is drawn, and only it should be compared.

| Visibility | What |
| --- | --- |
| `Gauge` | the first enabled generator's level, `master.level`, `voice.pan`, `comp.makeup`, `reverb.dry` |
| `Nuisance` | phase modes, start phases, seeds |
| `Disabled` | anything in a disabled module, and routes from or to one |
| `Dead(NotPulse, NotTable, SyncMaster, Silent)` | `pw` without the pulse wave; `position` and `table` without the wavetable; `sync` on the sync master; a generator at level 0 |
| `Dead(Unrouted)` | a modulator that drives nothing heard (env 2 and both LFOs in the starter) |
| `Dead(NeedsOctave, OneVelocity, OneKey, NoGlide, OneNote)` | keytrack without two notes an octave apart; velocity amounts and routes without two velocities; key routes without two keys; glide without a gliding phrase; voice mode, polyphony and LFO scope without notes that tell them apart |
| `Dead(BeyondHold, BeyondTail)` | an attack longer than the shortest hold; a release longer than the tail |
| `Dead(NoControls, ZeroDepth, HiddenEnd)` | routes from the mod wheel or a macro; depth 0; a route onto a hidden parameter |

### The minimum step

Each active category must move at least one counted draw by its step: cutoffs and other frequencies 2 semitones, LFO rates and times × 1.5 (times with 1 ms added), percentage levels 3 dB, dB values 3 dB, semitones 1, cents 3, other percentages 10 points, route depths 5 points, a discrete value or an enable flag any change. Otherwise the failing keys' attempt goes up by one and the category is drawn again; after 16 rounds its first counted parameter is set 1.1 steps from the start. Draws that depend on a level-5 choice (osc 2 and the noise, keytrack, velocity, voice mode) do not count, so they never change a lower category's attempts. In the 2,000 targets measured below, no step had to be forced.

## Sound score (lane SS)

`sound/1` (`enth_challenge::score::sound`, `calibrate`, `loudness`; lane SS, 2026-10-20) is the real sound score and this build's default (`RECREATE_SCORERS` names it). It decides pass. It is **provisional**: the curve comes from the owner's metric session 1 on the toy synth, and session 2 plus a real-engine pairs session refit it ([below](#how-sound2-replaces-sound1)).

### What it computes

| Step | Once per challenge (`prepare`, 0.25–1.8 s in release) | Per submit (`score`, about 40 ms) |
| --- | --- | --- |
| Patch | the target | the answer with its modules **renamed onto the target's ids** and the target's value at each **nuisance parameter** |
| Render | the phrase at `SCORING_SAMPLE_RATE` and `SCORING_SEED`, the mid channel | the same |
| Level | to −23 LUFS with the in-house `libm` loudness | the same |
| Features | metric v1.1's pooled log-mel (scalar FFT) and the descriptor readings | the same |
| Floor | the largest distance to 2 renders at other seeds (`floor_seed(1)`, `floor_seed(2)`), and the largest change of the pitch and odd-share readings | — |
| Scale | the median distance of the 16-copy jitter set, at least 0.01 | — |
| Score | — | `jnd` = max(0, d − floor) / scale + guard; `percent` = 100 / (1 + (jnd / 5.11)^1.338) |

**Pass is `jnd ≤ 0.989`**, which is `percent ≥ 90` (the pass mark). `SoundScore`'s `distance`, `floor` and `scale` are metric-v1.1 values; its `jnd` includes the guard, so the guard is `jnd − max(0, distance − floor) / scale`.

### The in-house loudness (`loudness`)

BS.1770-4 on `libm`: K-weighting (the shelf and the RLB high pass as two biquads in `f64`, from the analog prototypes, so any rate works; at 48 kHz the coefficients match the standard's tables within 1e-9), the mean square over 400 ms blocks every 100 ms, the −70 LUFS and −10 LU gates, and an ungated whole-clip fallback under one block; at or below −70 LUFS a clip is silent (`None`). Against `ebur128` it agrees within **1.8e-9 LU** on sines from 40 Hz to 12 kHz, the toy waves, noise, gated and stepped signals and ten rendered targets (`tests/ss_loudness.rs`). `ebur128` stays for display and true peak.

| Function | Use |
| --- | --- |
| `integrated_lufs(x, rate)` | the loudness; the scorer's, and what the worker measures both A/B sides with (the 48 kHz mid channel) |
| `gain_db(lufs, reference)` | **the one gain function** (P11): `reference − lufs` |
| `db_to_amp(db)`, `scoring_gain(x, rate)` | the linear gain; the gain to −23 LUFS |
| `ab_gains_db(target, mine)` | both sides to the quieter one's loudness: the louder attenuated, the quieter at exactly 0 dB, symmetric; `(0, 0)` when either is unmeasured. `enth_session::game::ab_gains` calls it |

### Metric v1.1, not v1

Metric v1.1 (`enth_analysis::pooled`, `logmel-pool85-l1/1`) is v1's log-mel with the mel magnitudes averaged over 85 ms blocks (4, 8 and 16 frames per resolution) before the log, then the same L1. It pools magnitudes as report 02's experiment did (the ADR says "power"), so report 02's numbers hold. On 40 generated targets (8 per level, `tests/ss_measure.rs`, release):

| | v1 | v1.1 |
| --- | --- | --- |
| Median floor / scale | 0.31 | **0.06** |
| Targets whose floor exceeds their scale | 13 of 40 (up to 2.65×) | 0 |
| A three-step cutoff move on such a target | z = 0 on all 13 (below the floor) | z up to 2.8 (0 where the cutoff sits far above the harmonics) |
| Median JND scale | 0.255 | 0.172 (by level 0.17, 0.12, 0.13, 0.16, 0.29) |

v1 cannot see real moves under its own floor on a third of the targets, so `sound/1` uses v1.1.

### Module mapping and nuisance parameters

Start phases and noise follow module ids, so the answer's modules are renamed onto the target's before the render. The prepared state keeps `matching::Matcher::for_round(ctx)`, and `SoundPrepared::scoring_patch(answer)` renders `matcher.relabel(&matcher.pair(answer), answer)` ([Module matching](#module-matching)), so SS and ST pair alike and routes come in the target's order (lane ST switched it on merging SS, replacing the local fallback; `ss_determinism`'s pin did not move). The free `scoring_patch(target, answer)` is the same with the context-free pairing.

The answer's **nuisance parameters** (lane RG's `Visibility::Nuisance`: phase modes, start phases, seeds) take the target's values in the scored render: an LFO retriggered at another start phase moved a level-4 score to 88 % before this, and P10 asks for at least 99. The generator never draws them, so they are not part of the challenge. The player still hears their own value.

### Calibration: the JND scale, the bridge and the curve

The jitter set moves every observable continuous parameter and route of the target by one step, up or down by a keyed sign (`calibrate::JITTER_SEED`):

| Unit | Step | | Unit | Step |
| --- | --- | --- | --- | --- |
| Hz, ratios, unitless | × 1.1 | | levels and sustain (%) | 2 dB over a 1 % floor |
| ms | × 1.1 over a 1 ms floor | | other % | 5 points |
| dB | 2 dB | | route depth | 2.5 points |
| cents, semitones | 10 ct | | degrees | 10° |

These are ADR-0007's "check's defaults to start" except pitch. `check`'s 25 ct is a pass band, not a step: the pitch difference limen near C3 is of the order of 10 ct, and a detune moved by 25 ct changes the beat rate many times over.

**The bridge.** Session 1 rated toy-synth pairs in metric-v1 distance (rating 4.5 at A = 0.26, rating 3 at A = 0.89; report 02 §2.2). Lane SS re-measured the spike's toy synth with these steps (`~/code/enth-scratch/r1s1/ss/bridge`; 40 targets of the spike's seeded list, 30 perturbed pairs each, built like the listening design's):

| Measured on the toy synth | Value |
| --- | --- |
| T1 (the spike's ±1 % jitter), first 20 targets | 0.1189 (the spike: 0.123), so the setup reproduces |
| Median JND scale, v1 / v1.1 | 0.2832 / **0.1629** (2.4 × T1) |
| Median v1.1 distance of pairs at A = 0.26 ± 15 % (148 pairs) | **0.1611**: rating 4.5 at z = 0.989 |
| Median v1.1 distance of pairs at A = 0.89 ± 15 % (89 pairs) | **0.8325**: rating 3 at z = 5.11 |
| Cross-check, per-pair z(v1.1) / z(v1) near the two points | 0.93 and 1.45: z = 0.85 and 4.56 |

**The curve** puts rating 4.5 on the pass mark and rating 3 on 50 %: `z50 = 0.8325 / 0.1629 = 5.11`, `k = ln 9 / ln(0.8325 / 0.1611) = 1.338` (`Curve::SOUND_V1`). Under v1 the same bridge gives z = 0.918 and 3.14.

### The pitch and waveform guard

Loudness-matched log-mel barely sees an octave or a waveform behind a filter. Before the guard, on level 1 (waveform plus octave): an octave-down saw scored z = 1.7 (81 %), and a 42.5 % pulse against the start's saw z = 0.86 (91 %), so **the untouched start passed**. So `jnd` adds `max(0, |Δpitch| − pitch floor) / 25 ct + max(0, |Δodd share| − wave floor) / 0.25`, each term only when both clips have the reading. A pitch error alone fails from about 25 ct, `check`'s "same pitch" band. A saw against a square is 2.6 JND. With it, **no start passes on 40 targets** (`ss_measure::the_start_by_level`: an octave off scores 3–5 %). This is lane SS's deviation from ADR-0007's "components beside the headline" (two components now feed it). Its units are provisional like the curve, for the real-engine pairs session to set.

### Components

One row per kind that either clip has, in `ComponentKind::ALL` order, read on **the phrase's first note** (from its note-on to the next note-on, with its note-off):

| Kind | Reading (unit) | One tolerance | Notes |
| --- | --- | --- | --- |
| `pitch` | YIN f0, else the tonal pitch (cents re A4) | 25 ct | feeds the guard |
| `brightness` | spectral centroid (Hz) | 10 % | |
| `harmonics` | odd share of the harmonic energy from h = 2, up to h = 16 (0–1) | 0.1 | feeds the guard; none for a sine; jumps near a 50 % pulse (a 45 % pulse reads 0.54) |
| `attack` | ms | 25 % over 5 ms | the descriptor resolves about 5 ms at C3 |
| `envelope` | decay to the sustain level (ms) | 10 % over 10 ms | |
| `sustain` | dB re the peak | 2 dB | |
| `release` | ms | 10 % over 10 ms | |
| `noisiness` | noise ratio (0–1) | 0.05 | |
| `movement` | the strongest of a detune beat, a tremolo (dB of wobble) and a filter LFO (6 dB an octave), Hz | 10 % | vibrato is not a reading |

Direction: `same` within one tolerance, else `higher` or `lower`; `missing` or `extra` when one clip lacks the reading. Badge: `close` under one tolerance, `a_bit` under three, `far` beyond. `component_text(&c)` gives the words, which never contain a reading: "brighter than the target", "attack slightly too fast", "pitch matches the target", "no movement; the target beats, wobbles or sweeps".

### Known limits

- **Detune** on two oscillators reads as decorrelation, not pitch, and not monotonically (report 02 §2.3), so the monotonicity test skips fine moves on multi-oscillator targets.
- **Envelope timing** stays mostly out of the headline. A short attack (5 → 20 ms) or a decay towards a high sustain barely moves v1.1; the attack and decay rows show it. An attack term is for the real-engine session to weigh.
- **The guard's pitch** is YIN's period. A target whose reading flips octave between its own nuisance renders gets a pitch floor of about 1200 ct, which switches the term off, but an answer that flips octave would be penalised.
- **First note only** for the components. On the octave and legato pairs the release is extrapolated or absent.
- **The calibration** is toy-synth ratings bridged through medians. The per-target scale varies (0.04–0.33 under v1.1 on the engine), and the bridge assumes the toy's and the engine's moves are rated alike at equal JND distance.

## Structure, combined and time (lane ST)

Lane ST, 2026-10-20: `score/matching.rs`, `score/structure.rs` and `score/combined.rs`. `RECREATE_SCORERS` names `structure/1` and `combined/1`; sound was still `sound-stub/1` then, and lane SS has since switched it to `sound/1`. The tolerances are generator v1's just-noticeable steps (`priors::jnd`). Lane SN's measured sensitivity (`enth_solver::sensitivity`) cannot feed them: `enth-challenge` is L4 and `enth-solver` L5. A scorer that takes measured tolerances, passed in by an L5+ caller, would be `structure/2`.

### Module matching

`score::matching` pairs the player's modules with the target's. Lane SS's scored render, the structure score and the rings use the same pairing, so a ring and the render agree on which module is the player's osc 1.

| Item | What it does |
| --- | --- |
| `match_modules(target, answer) -> ModuleMatching` | The context-free pairing of two patches: heard through the held phrase, nothing randomized (`enth compare` on two patches). F1R's signature, unchanged |
| `Matcher::for_round(ctx)`, `matcher.pair(answer)` | The round's pairing: built once in a scorer's `prepare`, then used on every submit. It weighs what the round randomized first. **SS and ST both use it** |
| `Draws::of(ctx)` | What the generator drew: the parameters, the routes and the enable flags. `TargetContext` carries only the parameters, so the generator runs again on the start (pure, about 0.3 ms) and must give `ctx.target` exactly. A hand-made context falls back to what the target changed from the start |
| `ModuleMatching` | `pairs`, `missing` and `extra` (present modules only), `answer_of`, `target_of`, `answer_addr`, `target_addr`, `answer_route`, `target_route`, `is_identity` |
| `matcher.relabel(&m, answer)` | **What SS renders.** The answer with every paired module renamed to its partner's id (seeds follow ids), with generators, modulators and routes in the target's order. Clashing unpaired modules get the lowest free `<prefix><n>`. Generators keep their order when the answer uses hard sync, and `voice_fx` and `fx` are chains, never reordered. A valid answer gives a valid patch. **Guarantee:** an answer that equals the target up to ids and order renders the target's samples bit for bit (`relabelled_equivalents_render_the_target_bit_for_bit`). `ModuleMatching::relabel` does the same but keeps the answer's route order |

**Present** is what takes part in the pairing:

- an enabled module;
- for a generator, not silent: a level above 0, or a route of non-zero depth on its level;
- for a modulator, live under the mask: the amplitude envelope, or the source of a non-zero route onto something heard.

So a disabled module, a silent generator, an unrouted LFO and a depth-0 route are absent: they pair with nothing and cost nothing. These are `canon`'s equivalences (disabled ≡ absent, depth 0 ≡ no route), applied to the patches as they are, so the player's real ids survive for the rings. Canonicalising first would relabel them.

**Pairing.** Modules pair per kind (oscillators with oscillators), so a permutation pairs by content, never by id, and the two amplitude envelopes always pair with each other. Each kind is an exact minimum-cost assignment: dynamic programming over subsets, since a section holds at most 8 modules. It pairs as many modules as the smaller side has. The cost compares three things, in order:

1. **The structure loss on what the round randomized:** Σ (1 − sᵢ) over the target module's randomized parameters, the randomized routes onto it (read by the source's kind, since the sources' pairing may not be known yet) and the randomized routes it drives. A target module left unpaired loses 1 for each such item, plus 1 when its enable flag was drawn. So the pairing is the reading that scores best for the player.
2. The same loss over the other parameters and routes that either side's mask calls observable. A hard-sync master paired with a non-master counts 1.
3. The number of renamed pairs.

Remaining ties go to the lexicographically first assignment: the target's modules in patch order, each taking the earliest answer module that keeps the optimum. Equal costs therefore keep ids and order. The kinds are paired in a fixed order:

1. the generators, twice: first against each patch's own first generator, then against the partner of the target's first generator (levels are ratios to it);
2. the effects;
3. the modulators, twice: route destinations map through the pairs found so far.

### `structure/1`

**What it compares:** only what the generator drew, all of it observable through the phrase (P4). Gauges, nuisances and dead parameters are never compared: nobody can hear them, and metric v1 measured `osc1.level` 100 → 50 %, `master.level` −6 dB and a 300 ms glide on one note at a distance of 0.0000.

| Item (one row) | Distance in steps | Row `addr` | `answer_addr` |
| --- | --- | --- | --- |
| A randomized parameter | Just-noticeable steps of the target's value against the player's partner's, with the folds below. Infinite without a partner | `filter1.cutoff` | The partner's address (`osc2.wave` for the target's `osc1.wave` when the oscillators swapped); `null` when missing |
| A randomized route | Depth difference in route steps (5 points); an absent route is depth 0. Infinite when an end's module has no partner | `lfo1 -> filter1.cutoff` (`RouteAddr`'s text) | The player's route, when it exists |
| A randomized enable flag | 0 when the player's patch has the module exactly when the target does, else infinite. A target module that is on is matched by its partner; one that is off by the absence of an extra module of its kind | `osc2.enabled` | The player's module of that row, `<id>.enabled` |
| A left-over module (`modules`) | Infinite, unless an enable-flag row already counts it | — | — |

**The folds** (the equivalences beyond matching):

- **Pitch:** an oscillator's `semi` and `fine` read as one pitch, 100·semi + fine cents. So +12 st ≡ +11 st and +100 ct, the semi row counts semitones and the fine row cents.
- **Levels as ratios:** a generator's level reads in dB against the target's first generator (in the answer, against that generator's partner; level 0 when it has none: absent ≡ silent). So every source 6 dB down is the same mix.
- **Wet against dry:** the reverb's `wet` reads against its `dry`.

Not folded: pulse at 50 % against the pulse wavetable (0.02–0.05 apart in report 02, not one of P8's), and the order of different kinds in an effect chain.

**Tolerances** are `priors::jnd`, generator v1's minimum steps, through `Jnd::steps`:

| Parameter | One step |
| --- | --- |
| Cutoffs and other frequencies | 2 semitones |
| LFO rates | × 1.5 |
| Times | × 1.5, with 1 ms added |
| Levels in % | 3 dB |
| dB values | 3 dB |
| Semitones | 1 (100 ct in the pitch fold) |
| Cents | 3 |
| Octaves | 1/6 |
| Other percentages | 10 points |
| Degrees | 30, wrapping |
| Route depths | 5 points |
| A discrete value or a flag | Any change is infinitely far |

They are "beta", like the levels: GR1's disputes tune them.

**Scores and rings:**

- **An item scores** `item_score(steps)`: 1 under one step (inaudible), else 1 − steps/4, reaching 0 at four steps. Report 02's curve is 1 within the tolerance, falling to 0 at four. Here the fall starts from the origin, cut at one step, because an integer semitone off is exactly one step: under report 02's curve it would score 1. This way it scores 0.75.
- **The ring** is `verdict(steps)`: good under one step, near under three, bad from three. **Structure % is 100 exactly when every counted ring is good.**
- **Structure %** = 100 × the mean item score over the counted items: every randomized parameter, route and enable flag, plus every left-over module not already counted by an enable-flag row. It is 100 when there is nothing to compare. Every item weighs the same in v1; weights from measured sensitivity would be `structure/2`.
- **Direction:** `same` under one step, otherwise `higher` or `lower`. For an enumeration it compares item indices. It is `missing` without a partner or route, and `extra` for an enable flag or route the target lacks.
- **Rows the player moved that the target did not randomize** (`randomized: false`) are shown when they are a step or more off, and never counted. They cover the target's other observable parameters, the target's other heard routes, and the player's heard routes between paired modules.
- **Row order:** randomized parameters (address order), randomized routes, enable flags (id order), then the moved parameters and moved routes. `modules` lists the missing ones (target order), then the extra ones (player order).

**What the editor and the CLI need to know:**

- **Route and enable-flag rows do not parse as `ParamAddr`.** Parse a route with `RouteAddr::from_str`, and strip `.enabled` for a module's switch.
- The session's `knobs()` skips both, as it skips any address it cannot parse, so they show only once RUI rings routes and switches.
- `score_structure` needs no render: it costs one mask and one pairing, so the live rings after the first submit are cheap.

**Accepted consequences:**

- An enabled extra module can *raise* an off-target answer's score. When it fits the target better than the player's own module, the matching reads it as the partner, and the player's module becomes the extra term.
- Disabling a module also removes what only it made heard: with the filter off, env 2 (which only drove the cutoff) is missing too.

### `combined/1`

combined = (w·sound + (100 − w)·structure) / 100, where w is the challenge's `sound_weight` in percent. The weight lives in the challenge, so a later default never moves an old score.

The Recreate default is lane CT's `ScoringSpec::recreate`: w = 50 + 30·difficulty/100, with integer division.

- **50 % at difficulty 0:** structure is unambiguous there, and ADR-0007 asks to lean on it.
- **80 % at 100:** many routes are valid there.

The formula puts the integer weight first, so 65·90 + 35·80 = 8650 → 86.5 exactly. `CombinedV1::percent(w, sound, structure)` is the same formula for the CLI.

**It never decides pass:** `ScoreReport::new` decides pass from sound alone (`combined_never_decides_pass`).

### `time/1`

Time to pass is the first passing **submit**, in the editor-visible milliseconds the shell's clock gave the session. Core crates read no clock. It counts submits, not a live pass, because a live pass light would give the answer away.

- `score::combined::time_to_pass(submits)` is the rule as a pure function over `Submit { at_ms, passed }`, taken in submit order; it is `None` without a pass.
- `first_passing(log, passes)` replays any timed log ("you were at a pass at 1:42").
- The session (lane SG) keeps the same rule on its own (`time_to_pass_ms` is set on the first passing scored submit).

## Golden challenges (lane GC)

25 challenge codes, pinned with the target they regenerate and what the scorers say about three fixed answers each. They are the end-to-end check on the game's logic: a change anywhere between the code and the percentage moves a pin, on every platform at once. The harness is `tests/golden/src/challenges/` (tooling, not a core crate); the data is `tests/golden/challenges/`; the test is `tests/golden/tests/gc_challenges.rs`.

```text
tests/golden/challenges/
  cases/<name>.toml      the input: a code, a description, recipes for the answers beyond `exact` and `start`
  expected/<name>.txt    the pins, written by `cargo xtask golden --challenges --update`, never by a test or CI
```

### A case

```toml
description = "Level 1, seed 1: a triangle wave at the start's pitch (two randomized parameters). Near: the pitch 0.1 semitone off."
code = "1040-1000-0000-1R"        # short or long form; written canonically (uppercase), checked against its own re-encoding
scorings = ["v1"]                  # the default; `stub` names the parameter-space stand-ins (below)

[answers.near]                     # at most two answers beyond `exact` and `start`; those two names are reserved
add = { "osc1.semi" = 0.1 }        # applied in order: base, enable, set, mul, add, depth
```

`exact` is the target's own patch, `start` is the round's start patch, and a recipe starts from either (`base = "target"` is the default) and moves it by `enable` (`{ osc2 = false }`), `set`, `mul`, `add` (on `module.param` addresses) and `depth` (a route's depth, `"lfo1 -> filter1.cutoff" = 40.0`). Recipes go through `enth_patch::apply`, so a recipe that the patch model would refuse fails the case.

### What is pinned

| Part | Pinned as |
| --- | --- |
| The code | the code, its form (short, or long with its engine version), the spec it decodes to (generator, seed, difficulty, musical, template, the six amounts), the level and the phrase |
| The target | the **fingerprint** (never a patch hash: it moves only when the target does, [the fingerprint](#the-target-fingerprint)), the counts of what the generator drew, the target's integrated loudness, and the SHA-256 of the scored render (to tell a render difference from a scoring one) |
| Each answer, per scorer set | sound %, structure %, combined %, pass, the margin; sound's distance, floor, scale, jnd; each component's direction, badge and both readings; each ring's verdict (`good`, `near`, `bad`) and the moved parameters; the module terms |

Numbers are compared within 1e-6 (relative for readings), which stands for the printed digits only: the scorers are bit-exact. The harness also prints one SHA-256 over every case's unrounded numbers (`bits`); it is not a pin, but a native and a wasm run print the same one.

Every challenge is built with `ScoringSpec::with_scorers` and the scorer ids named in the block's heading (`scoring sound/1 structure/1 combined/1 time/1 weight=50 pass_mark=90`), so a new default scorer never changes a golden.

### The margin

No pass or fail decision may sit within **1e-3** of the pass mark (`margin::check`, on every answer of every block). The scorers are deterministic, but a gain that moves in its last bit should not be able to flip a pinned decision unnoticed. A case within the margin fails, in a check and in an update, with the case, the answer, the sound % and the way out: change the answer's recipe, using `cargo run -p enth-golden -- --challenges --propose <code or settings>`, which prints a code's target facts, its randomized parameters and the start's score, then the target moved by a few amounts one parameter at a time with the sound and structure % and a `!` on any move within the margin. The pinned cases keep at least 0.04 from the pass mark. Tested with a deliberately too-close case (`the_margin_refuses_an_answer_too_close_to_the_pass_mark`, built by bisecting a pulse width to within 0.00025 of the mark) and at the boundary (`the_margin_is_one_thousandth_either_side`).

Only the pass mark has a margin. The structure ring verdicts (`good` under one step, `near` under three) are exact arithmetic on steps, not a threshold on a float score.

### Updating

`cargo xtask golden --challenges --update` (refused under `CI`):

- A case with no `expected/` file gets one.
- A case that lists a **new scorer set** gets a new block beside the old; the old block is kept byte for byte.
- Anything already pinned that would change is **refused**, with the lines that differ and this text: a pinned result never changes under the same scorer ids; a change is a new scorer id (a new block), never an edit. The deliberate exception is the case that has never been shared (the generator or the engine moved before any code was handed out): delete its `expected/` file, update, and say why in the commit.
- An `expected/` file with no case is reported stale and not deleted.

`--only <case>` restricts a check or an update to one case. `cargo xtask golden --challenges --wasm` runs the same checks under wasmtime.

### Findings while choosing answers

- `sound/1` steps by a few thousandths where a pitch offset crosses a decision in the analysis (level 1 seed 1: 90.0019 just below an offset of 0.17550 semitones, 89.9988 just above), so a pitch bisection can straddle the pass mark without landing in the margin band. Pulse width is smooth; the too-close test uses it.
- A start can be close to a pass: `l1-s11`'s starts at 87.8 % (2.2 under the mark) and `l2-s11`'s at 75.1 %. The pins hold the exact numbers, and the invariant test requires only that no start passes.
- A silent target gives every silent answer 100 % (`silent-l2-s23`); its start is silent too, and the near miss passes. **Fixed for play** (R1/S1 lane INT): `prepare_round` refuses such a target (`silent_target`), so the plugin, the Recreate UI and the CLI never play one; the editor deals a round it dealt again with a fresh seed (up to 8 in a row), and a pasted code says why. Generator v1 stays frozen (a render-based redraw would need an attempt index in the code). The golden case stays: `prepare_challenge` scores it as given.
- Envelope parameters barely move `sound/1`; the near misses are pitch, pulse width, cutoff and rate offsets.

### Joining lane SKR's five

`tests/golden/challenges/skr-v1.txt` (lane SKR) pins the stub scorers' columns for five of the codes here (`1R`, `PJ`, `DG`, `WC`, `3Q`) in its own format. The two files do not touch. To move them into this format, list `scorings = ["v1", "stub"]` in those five cases and run `--update`: the `stub` set (`sound-stub/1 structure-stub/1 combined-stub/1 time/1`) is added as a second block, beside the pinned `v1` one.
