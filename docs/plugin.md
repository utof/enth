# The plugin (`enth-plugin`, L8)

**`enth-plugin` is the CLAP and VST3 shell around [`enth-session`](session.md), `enth-engine` and `enth-ui`, on nice-plug `=0.4.2` and nice-plug-egui `=0.6.0`.** It translates between the host and the product: 72 host parameters, notes, audio blocks, the saved state and the editor window. It holds no product rules: what an edit does, when a host value enters the patch and how a plan reaches the engine are the session's ([session.md](session.md)). Lane SK built the walking skeleton (freeze point F2b, [phase-1b.md](phase-1b.md)); lane PL completed the plugin (this page's state is PL's, 2026-10-20, with lane FK2's fork follow-ups: dirty marking, the VST3 MIDI CC list, the rescan off `process()`, no restart on a render-mode change); ED1 and ED2 build the editor, RH the REAPER scenarios. Decisions behind it: [ADR-0001](adr/0001-plugin-shell.md), research report 01 in `_local/sessions/2026-10-19-p1b-plugin-editor/`.

## Identity

- CLAP id `dev.enth.synth`, VST3 class id `55555EAD-AA77-C9FA-F878-DDDDB0B9D9BD`, name "enth", vendor "enth" ([naming.md](naming.md); a test pins both ids). REAPER lists it as `CLAPi: enth (enth)` and `VST3i: enth (enth)`.
- 72 parameters in host order: `macro_1`…`macro_8`, then `slot_1`…`slot_64` (`#[nested(array)]`, the order of `enth_session::bridge::HOST_PARAM_IDS`). nice-plug hashes them to the ids hosts store: `macro_1` 825615486, `slot_1` 1248030256, `slot_64` 34232479, the same as the shell spike's (tests pin them, and `reaper-test` checks REAPER's idents).
- Each is a linear 0–1 `FloatParam` with no smoothing (the engine smooths). Macros default to 0 and take CLAP poly-mod (id = macro index); slots default to 0.5. The names fixed at construction are "Macro N" and "Slot N"; at run time they follow the patch ([Parameter names](#parameter-names)).
- Stereo out, no audio in. `MIDI_INPUT = MidiCCs` ([MIDI CCs](#midi-ccs-the-decision)): the mod wheel plays; VST3 lists 16 more (hidden) parameters, CC 1 on each MIDI channel (`VST3_MIDI_CONTROLLERS`, the fork's patch 7). `SAMPLE_ACCURATE_AUTOMATION = true` (required, [Determinism](#determinism)). `CLAP_POLY_MODULATION_CONFIG` is 32 voices, overlapping; CLAP voice info reports the running plan's voice count ([below](#voice-info)).

## Threads

| Thread | Runs | Touches |
| --- | --- | --- |
| Audio (`process`, `reset`) | [the block](#the-audio-block) | the `Engine`, the `Audio` state (event list, [ledger](#note_end)), the atomics in `Shared`, the parameters' atomics. **Never the session lock** |
| Host main thread | `activate`, `deactivate`, state save and load (the persistent fields) | the session, through `Shared::with_session` |
| baseview's GUI thread | the editor's `build` and `ui` | the session, through `Shared::with_session`; `ParamSetter` after unlocking |
| nice-plug's background worker | `Task::Pump` | the session (pump, audition release) |
| the game worker (`enth-game`, lane SKR) | a round's jobs ([below](#the-recreate-round-lane-skr)); spawned at the first job, joined when `Shared` drops | its own queues and the target loop's hand-off. **Never the session lock** |
| the create thread (`enth-create`, lane SK3, feature `create`) | a create job from the file to its last post ([below](#create-lane-sk3-r3)); spawned at the first job, joined when `Shared` drops (it cancels the running job first) | its own queue and posts, the audition hand-off. **Never the session lock** |
| a job's pool (`enth-search-N`, `min(cores / 2, 8)` threads) | the K searches' renders, distances by index | built per job with `build_scoped` and **joined before the job returns**: no search thread exists between jobs |

`Shared` holds the one lock, `parking_lot::Mutex<Session>`, and atomics: `pump_wanted`, `monitor_bypass`, `rebaseline`, `editor_closed`, plus a weak reference to the parameters for reading the host's values off the audio thread, the fork's `HostRequests` (set once by the wrapper right after construction, `Plugin::host_requests`) and, with `rt-stats`, the histogram. **`Shared::with_session` is the only way in:** it locks, runs the closure, drains the session's requests, sets the 72 display names if one of them was `RenameParams` ([below](#parameter-names)), notes whether a compile is still pending, **unlocks**, then stores the monitor bypass, asks the host for a parameter-info rescan on a rename, marks the project dirty on `PatchEdited` ([Dirty marking](#dirty-marking)), arms `pump_wanted`, and returns the host writes. Only editor edits make host writes, and the editor forwards them to `ParamSetter` after this returns, never under the lock, because a host may call back synchronously (to read the state, which locks).

## Lifecycle

- **Construction.** A `Session` on [Init](#the-init-patch) (`init::patch()`; `Patch::init()` until lane AM), the parameters, the editor state (sized by the theme's `size.window.default`), and an `Audio` whose event list and ledger are allocated here, never in `process()`.
- **`activate`** (main thread). Fold the host's values into the patch (`Session::fold_host`), then `Session::activate` (compile, `Engine::with_link` with `RENDER_SEED`, a disabled telemetry tap, the persisted monitor bypass on the fresh engine). The engine replaces the previous one, which drops here on the main thread. CLAP voice info gets the plan's voice count (`set_current_voice_capacity`). `Audio::activate` takes the host's current values as "last sent", so nothing is echoed and the engine starts from the patch, forgets the old engine's live notes (the host forgets its voices at deactivation, and a `NOTE_END` can only go out from `process()`), and clears `rebaseline` (this is the re-baseline a load before activation asked for). A sample rate outside the engine's 8–384 kHz activates **silent**, with the session detached, rather than failing: clap-validator sweeps 1 kHz to 768 kHz and a host that refuses a plugin is worse than silence.
- **`reset`** (audio thread; nice-plug also calls it at CLAP `start_processing` and VST3 `setProcessing(true)`). `Engine::reset()`, which frees the voices and empties the engine's queue without reporting them; the next block reports every live host note's `NOTE_END` at frame 0 ([the ledger](#note_end)).
- **`deactivate`** (main thread). `Session::deactivate`, then the engine drops. With `rt-stats`, the histogram's report is written ([below](#rt-stats)).
- **Offline renders.** `CLAP_RESTART_ON_RENDER_MODE_CHANGE = false` (the fork's patch 9): when a CLAP host switches the active plugin to offline rendering, nice-plug no longer asks it for a restart. REAPER does that switch at the start of every offline render and used to honour the restart about 30 ms of wall-clock time later, mid-render: a fresh engine continued the render and the note sounding there was lost, at a point that depended on the render's speed (the `clap/macro-automation` flake, [ADR-0001](adr/0001-plugin-shell.md)). The engine renders the same in both modes; the cost is that `Activation::offline` keeps the mode of the last activation, so in such a CLAP bounce the editor's audition notes are not refused (VST3 hosts set the mode before activating, so nothing changes there).

## The audio block

`Enth::process_block`, in order; nothing allocates, locks, logs or does I/O (nice-plug's `assert_process_allocs` aborts a debug build that does, and clap-validator and the test host's checks run the debug bundle):

1. **Host values.** Read the 72 parameters' modulated normalised values and send each one that changed since the last block as `EventKind::Macro { index, value }` or `EventKind::Slot { slot, value }` at offset 0. Never a bare `EventKind::Param`: a plan swap inside the block would misroute an id looked up before it. The modulated value lets the engine follow CLAP mono modulation while the patch keeps the unmodulated one. With sample-accurate automation nice-plug splits the host block at each parameter change, so offset 0 is the change's own frame. After a state load (`rebaseline`) the values are adopted without being sent.
2. **Reset ends.** After a `reset`, every live host note's `NOTE_END` at frame 0.
3. **Notes and render.** The monitor bypass goes to the engine, then the block's note events ([Notes](#notes)) into the event list (nice-plug's input capacity plus 72, 1,096 events) and `Engine::process`. **No host event is dropped:** when the list is full, the frames up to the event that did not fit are rendered with the list, and the list starts again from there. The engine renders the same bits for any split of a block (its grid is free-running), so this is invisible. After each chunk its `NOTE_END`s go out through the [ledger](#note_end), at their frames in the host block.
4. **Telemetry**: the tap's wake flag becomes a repaint request (lock-free).
5. **Editor closed**: `EguiEditorState::is_open()` falling disables the tap and sets `editor_closed` and `pump_wanted`; the next background pump releases audition notes. (The vendored nice-plug-egui also calls the editor's `editor_closed`, which does the session side on the GUI thread; both are idempotent.)
6. **The pump flag** ([below](#the-pump)).
7. **Voice info**: when a plan swap changed the plan's voice count, report it (`set_current_voice_capacity`).

Step 7 calls nice-plug's own process-context function, which queues one of nice-plug's main-thread tasks and calls the host's `request_callback`; only a host that calls `process()` on its main thread gets the task inline (a host call: `voice_info.changed`), so it is wrapped in `permit_alloc` for the host's own work. It runs none of our code, takes no lock of ours and allocates nothing on our side. `execute_gui`, which would run **our** task inline, stays banned. The parameter-info rescan is no longer asked for here ([Parameter names](#parameter-names)).

### Notes

A host note is `NoteKey { port: 0, channel, key, note_id: VoiceID::id() or −1 }` (`VoiceID::id()`, never `id_or_fallback`, which `clippy.toml` bans). In a note-off or choke a wildcard field is −1, the engine's wildcard; a note-on needs a key (a wildcard key is dropped) and takes channel 0 for a wildcard channel. Host notes are on port 0, so a host note-off never releases an editor audition note (`AUDITION_PORT`).

- **Zero-length notes.** A note-off the host lists ahead of the note-on with the same note id on one frame is moved behind it, so the note starts and ends (the order `enth render` gives a zero-length note) instead of starting after its own note-off and hanging. A note-off for another note id on that frame (a retrigger) is not moved. The test host's `note-end` script has such a note (`D4@0.25+0.00001` rounds to zero frames).
- **Poly-mod.** `PolyModulation` becomes `EventKind::MacroVoice { key: NoteKey::note_id(voice_id), .. }` for macros 0–7: only the voice whose note carries that host id moves (tested: id 9 moves, id 7 and an unknown id 1234 do not). nice-plug sends poly-mod only for a real note id; an id of −1, which would be the engine's wildcard, is dropped. `MonoAutomation` is ignored (step 1 already reads the modulated value). A note-on starts its voice's offsets at 0, so a modulation sent before the note starts waits for the host's next one.
- **MIDI CC 1** (the mod wheel's MSB), on any channel, becomes `EventKind::ModWheel` with nice-plug's `cc / 127`. Other CCs, CC 33 (the wheel's LSB), pitch bend and pressure are ignored: the engine has no input for them yet.

### `NOTE_END`

**Every host note-on gets exactly one `NOTE_END`**, with the note's own tuple (`VoiceTerminated`; nice-plug writes port 0; VST3 drops it). Hosts that track voices, and CLAP poly-mod, rely on it. The engine reports a voice's end, but some notes end without a report: more than 256 voices ending in one `Engine::process` call (an event flood: the engine counts the rest in `dropped_note_ends`); in mono and legato the one voice takes the new note's key, so the note it played before is never reported (and a return to a held key brings an already-replaced key back); and a note-on still waiting for its segment boundary when a reset empties the queue. So `ledger.rs` keeps every live host note (its tuple and the frame of its note-on). After each chunk: an engine report for a live note is sent and the note forgotten; a report for a note that is not live (already reported, or an audition note) is not sent again; then a **sweep** reports every live note whose note-on the engine has applied (the segment boundary after its frame has been rendered) and that no active voice plays, at the chunk's last frame. At a reset all live notes are reported at frame 0 of the next block.

In mono and legato the replaced note's end is therefore reported when the voice takes the new note, and a return to the held key does not end it twice. Cost: one scan of the active voices per live note per chunk (a few dozen comparisons while playing); the list holds 4,128 notes (the engine's queue plus every voice).

## Parameter names

On every `ShellRequest::RenameParams` (the session pushes it only when the host would see other names or kinds, and on every load), `Shared::with_session` sets the 72 display names from the patch with `enth_session::bridge::host_param_name` ("Filter 1 · Cutoff", a macro's own name; "Slot 7" for an empty slot), through lane FK's fork (`Param::set_display_name`; a name equal to the construction name clears the override). It does so **under the session lock**, so two threads that rename one after the other (an editor edit on the GUI thread, a host load on the main thread) always leave the later patch's names; `set_display_name` only stores a string behind the parameter's own lock and calls nothing, so the lock still never calls the host.

The host is then asked to re-read them, right after unlocking, on the thread that renamed (lane FK2, the fork's patch 8): `Shared::settle` calls `HostRequests::request_param_info_rescan`, which nice-plug performs on the host's main thread: CLAP `clap_host_params.rescan(INFO | TEXT)`, VST3 `restartComponent(kParamTitlesChanged)`. A host state load runs on the main thread, so the rescan happens during the load, before the host processes the loaded state (as nice-plug's own `rescan(VALUES)` after a load does); an editor rename on the GUI thread is queued for the main thread. One queued request absorbs the next.

- **Never from `process()`** (design.md §4). Until patch 8 the fork offered the request only on the process and GUI contexts, so PL asked for it from the next block after a load. nice-plug's `schedule_gui` runs the task inline when the calling thread is the one it treats as main, and a CLAP host may make its main thread the audio thread (an offline render may): the host's `rescan` would then be called from inside `process()`. On VST3 under Linux, with the editor closed, the request from the audio thread went to nice-plug's background thread instead, off the UI thread. The in-process host's fake process context now panics on a rescan request.
- **Measured in REAPER 7.82** (`reaper-test`, `state-create`, which loads `enth-state.patch.json` with a named macro and two slots on a labelled filter): **CLAP** shows "Bright", "Tone · Cutoff", "Tone · Resonance" after the load (checked after the scenario's 1.5 s wait; `param-renamed`). **VST3 shows them too, and at once:** REAPER ignores `kParamTitlesChanged` (as the Phase 0 spike found) but reads VST3 parameter titles live, so the fork's override reaches it anyway. The earlier note that "VST3 in REAPER stays Slot N" was about the title-change message, not what REAPER displays. An automation lane that already exists keeps its label but stays bound by id.
- **Not done: value text.** A slot's value is shown as the plain 0–1 number. Showing the target's units ("1.2 kHz") needs a `value_to_string`/`string_to_value` pair per slot that reads the slot's current spec; clap-validator's `param-conversions` test checks that text → value → text round trips, which rounding display text can break. Left open.

## MIDI CCs (the decision)

**`MIDI_INPUT = MidiConfig::MidiCCs`** (lane PL, 2026-10-20; it was the open check "decide `MidiCCs` before the first build leaves the machine"). With it the mod wheel (MIDI CC 1) reaches the engine in both formats; with `Basic` nice-plug drops every CC, so a patch's `modwheel` routes would never move. CLAP pays nothing. For VST3 stock nice-plug registers 130 × 16 = 2,080 hidden, read-only parameters (`IMidiMapping` maps a CC to one, nice-plug turns its changes back into `MidiCC` events), and REAPER lists them: it reads them as not automatable, so it sees the flags, but keeps hidden parameters in its list.

**Narrowed to CC 1 (lane FK2, the fork's patch 7).** `Vst3Plugin::VST3_MIDI_CONTROLLERS = [1]`: the plugin maps only the controller `notes::engine_event` reads (a test tries all 130 and keeps the two in step), on all 16 channels, so REAPER lists 91 parameters on VST3 ("MIDI Ch. 1 CC 1" … "MIDI Ch. 16 CC 1" after the 72; `reaper-test`'s `state` checks the names). The mapped parameters keep their ids, and the mod wheel plays as before (the `mod-wheel` scenario: level 0.403 with the wheel down, 0.000 with it up, on both formats; `cli-equal`'s `mod-controls` equal). Pitch bend (controller 129) joins the list with its engine input.

| Measured (REAPER 7.82 headless, Xvfb, 10 instantiations each) | `Basic` | `MidiCCs` |
| --- | --- | --- |
| Parameters REAPER lists, CLAP | 75 | 75 |
| Parameters REAPER lists, VST3 | 75 | **2,155** ("MIDI Ch. 1 CC 0" … after the 72); **91** with patch 7 (CC 1 only) |

Why on: the mod wheel is a modulation source of the patch model (routes from `modwheel`, a golden case, the CLI's `controls`), CLAP is the first format and pays nothing, and the VST3 cost was a longer parameter list in REAPER and a couple of milliseconds per instantiation (now 16 entries). To undo it, set `MIDI_INPUT` back to `Basic` (and `reaper-test`'s VST3 `param-count` back to 75 and its `mod-wheel` scenario off). Hiding the CC parameters from VST3 altogether would have cost the VST3 mod wheel; patch 7 keeps it.

## Dirty marking

nice-plug never told the host about a change it cannot see, so REAPER kept the project clean after an editor-only patch edit (lane RH's `dirty-flag`: `IsProjectDirty` 0 on both formats). With the fork's patch 6 (lane FK2), `Shared::settle` turns the session's `ShellRequest::PatchEdited` (an editor edit, undo or redo, once per drain) into `HostRequests::mark_dirty`: CLAP `clap_host_state.mark_dirty`, VST3 `IComponentHandler2::setDirty(true)`, both on the host's main thread (queued from the GUI thread; one queued request absorbs the next, so a drag costs one host call per main-thread turn). A slot-bound edit also moves a host parameter, which dirties the project anyway. Host loads and folds push no `PatchEdited` (unit test). Measured: `IsProjectDirty` 1 at once and 3 s after an editor-only edit on CLAP and VST3, 0 with the editor open and no edit.

An editor preset load, and its undo and redo, push `PatchEdited` too (`Session::deliver_load`; a unit test in `src/presets.rs` counts one `mark_dirty` each through `Shared::with_session` and no host write). Not marked: the monitor bypass and the editor preferences in the `enth` field (the session pushes `MonitorBypass` on host loads too, so the shell cannot tell a user's switch from a load).

## Voice info

CLAP voice info reports the running plan's voice count: its polyphony in poly mode, 1 in mono and legato (`process::voice_count`), at `activate` and whenever a plan swap changes it (step 8). The capacity stays the engine's 32 voices, overlapping.

## The pump

A compile that the session could not send (two plans in flight: the host had stopped calling `process()`) waits for the session's next entry. With the editor closed there may be none, so ([session.md](session.md), "Plan delivery"; F1b decision 1):

- whoever unlocks the session with `compile_pending` set arms `pump_wanted` (`Shared::with_session` does it for every caller);
- `process()`, while the flag is set and at most once per `PUMP_INTERVAL_S` (50 ms) of audio, clears it and calls `execute_background(Task::Pump)`: one bounded `try_send` to nice-plug's worker, only while a compile is pending, never in steady state;
- the task locks the session, releases audition notes if the editor closed, pumps, and re-arms the flag if a compile is still pending.

Never `execute_gui` from `process()`: it can run the task inline (CLAP `request_callback` while the host calls `process()` on the main thread). `clippy.toml` bans it in the crate.

## The monitor bypass

The global FX bypass ([ADR-0006](adr/0006-effects-strategy.md)) is per-instance state outside the patch: `InstanceState::monitor.fx_bypass` in the `enth` field. The editor switches it with `SessionEdit::set_monitor_bypass`; the session pushes `ShellRequest::MonitorBypass`, `Shared` stores it in `monitor_bypass`, and every block hands it to the engine (`Engine::set_monitor_bypass`), which fades the `time_based` effects (the reverb) out or in over 20 ms. A loaded `enth` field reaches the engine the same way; on a fresh engine (a project opening with the bypass on) the switch is immediate. Tested: with the bypass on from the saved state the render equals `enth render` of the patch with its reverb disabled, bit for bit at host blocks 64 and 100, and through the test host the `monitor-bypass` and `reverb-off` host-render cases give one hash; switched on mid-render through the session, the engine fades for 20 ms and the setting is saved in `enth`, not in the patch. The editor's control is ED1's.

## State

nice-plug saves `{"version", "params": {id: {"f32": v}}, "fields": {...}}`; the CLAP stream is a `u64` length and that JSON. Two fields, both permanent names:

| Field | Text | On load (host main thread) | On save |
| --- | --- | --- | --- |
| `enth` | `InstanceState::to_json()`, `enth.plugin-state/1` | `Session::load_instance`; the monitor bypass reaches `process()` through `Shared` | `Session::save_instance` |
| `patch` | exactly `Patch::to_json()`, carried as a `serde_json::value::RawValue` (the `raw_value` feature; no extra crate), so it is neither escaped twice nor re-parsed | set `rebaseline`, `Session::load_patch` (the patch wins; its plan goes out at once and forgets the engine's remembered host slot values; the names are set), then `fold_host` with the restored values, which only records them | `Session::save_patch` with the host's values: folded first (rule 2 and 3 of the bridge), then the patch text, or the kept text of a patch that did not load |

nice-plug sets the parameters first, then `enth`, then `patch`, and neither re-activates nor resets after a load, so the engine is kept and the session sends the loaded patch's plan itself. **Host values are re-baselined on load:** the restored values never reach the engine as host events, while a value the host sets after the load does, even in the very next block. The `patch` field's `set` stores the values nice-plug restored (`process::Restored`, a small seqlock) before it raises `rebaseline`, and the next block takes exactly those as "last sent". (SK's first version adopted whatever the host held at that block; REAPER loads a project's state while the plugin is active and sends an automation lane's value once, in the first block, so a lane that never moves was lost: lane RH's flat-lane finding, traced by PL.) Tested: after a load with slot 1 restored to 0.9 the engine remembers no host value for slot 1 and a later change to 0.3 reaches it; a change to slot 64 in the first block after a load reaches the engine and, once the level smoothing lands, sounds exactly like the patch with that level, which the old adopt-everything fails. A `.patch.json` file and the `patch` field are interchangeable: the test host's `--state some.patch.json` puts the file's text into the field, and the plugin saves it back byte for byte (`render --save-state F --check-roundtrip` reports `identical_text: true` for `enth-plugin.patch.json`).

**Never `GuiContext::set_state`** (nice-plug applies it on the audio thread while processing, where the field would lock and compile) **or `GuiContext::get_state`** (it serialises the fields, which lock: a deadlock inside an editor frame). An editor preset load calls `Session::load_preset` (docs/presets.md) under the lock on the GUI thread; the host's values do not move, and the next frame's fold records them as the baseline (stale ones never enter the new patch).

The editor is ED1's ([editor.md](editor.md)): `src/editor.rs`'s `Glue` wraps `enth_ui::editor::Editor`. **Loudness and gains.** Both sides of the A/B are measured with lane SS's `enth_challenge::loudness::integrated_lufs` on the 48 kHz render's mid channel (`game::integrated_lufs`); the session turns the two readings into gains with the scorer's own `gain_db` (`game::ab_gains`, P11), and the shell converts the dB values with `loudness::db_to_amp` on the thread that drained them. The louder side is turned down; the quieter one is never boosted.

**The target loop's hand-off** (`Mailbox`): an incoming and a retired slot, each an `AtomicPtr` to a boxed `TargetLoop` (the loop's frames and the phrase's notes in frames at the loop's rate). Only the worker publishes (so a clear, the empty loop sent when `AbState::target_ready` turns false, and the next round's loop arrive in order); a loop the audio thread has not taken yet is freed by the publisher. The worker, each editor frame and `Drop` collect retired loops.

**`Player`, in `process()`** (around the render; [The audio block](#the-audio-block)):

1. Before the render: read the A/B atomics, take a new loop, follow the switch. While Target ▶ or Mine ▶ is on, **Mine's phrase** runs: its notes go into the block's event list at their loop positions, on note port `game::GAME_PORT` (`0x7F01`), so a host note-off never releases them and the `NOTE_END` ledger never reports them; they keep playing, muted, under Target ▶, so a flip is instant. A loop at another rate than the host's never plays (the GUI frame asks the worker for one at the host's rate after a re-activation).
2. After the render: `out = engine · gain_mine · (1 − w) + loop · gain_target · w`, at one shared position (the loop's), every factor ramped over `AB_FADE_MS` (10 ms). Off: the phrase's notes are released and the gains settle back to unity.
3. **While no round plays (or the switch is off and the ramps have settled), the player returns before touching a sample**: four atomic loads and one pointer swap per block. So a plugin render still equals `enth render` bit for bit, `host-render` and `cli-equal` are unchanged, and the in-process host tests pass untouched.

**Target ▶ is the scored audio**: at 48 kHz the loop is exactly the render the scorer hears (`tests_game.rs` compares it sample for sample, scaled by the level-match gain); at another rate the same patch and phrase rendered at the host's rate.

**Transport.** REAPER keeps calling `process()` while its transport is stopped (lane PBU's check), so Target ▶ and Mine ▶ play with the transport stopped there; other hosts are an open check.

**The round log.** Each `GameRequest::Log` line (`enth.round-log/1`) is appended, one write per line in append mode, to `$ENTH_ROUNDS_DIR/round-log.jsonl` when set, else `<Documents>/enth/Rounds/round-log.jsonl` (beside the crash folder, `<Documents>/enth/Crashes`; `game::round_log_path`). **The `ab-toggle` measurement harness** (cargo feature, off by default; never in a shipped build): with `ENTH_AB_TOGGLE_MS` set, activation starts a round (`ENTH_AB_CODE`, else level 1 with seed 1), waits for its target and turns Target ▶ on, and `process()` flips Target ▶ and Mine ▶ itself every that many ms of audio; at deactivation one `enth.plugin-ab-stats/1` line goes to `ENTH_AB_REPORT`. `enth-test-host process-stats --ab MS` sets both variables before it loads the plugin and reads the report back (it fails when the bundle has no harness or the A/B never flipped).

### The hint evaluator (lane HINT, FU1)

`src/hint_eval.rs`. The coach's renders (`CoachTarget::for_round`'s sensitivity batch, the plan's probe batch and its serial verification steps) go through `hint_eval::Workers`, the plugin's `enth_solver::Evaluator`: `enth_solver::measure` on scoped threads (`std::thread::scope`; no new crate), one shared atomic counter as the work queue, each result written back at its job's index, so **a hint is identical for any worker count** (each result is a pure function of its job on the scalar FFT path; `the_worker_count_never_changes_the_hint` compares eight hints for 1 and 3 workers, `results_come_back_in_job_order_for_any_worker_count` compares batches with an error at its index for 1, 2, 3 and 8). Each worker keeps its `Describer` across batches; the game worker's own thread is worker 0, so a batch spawns `n − 1` threads (`enth-hint-<i>`) for its length only, and a batch of one job, or one worker, runs inline.

**How many** (`hint_eval::hint_workers`): half the logical CPUs, at least 1 and at most `MAX_HINT_WORKERS` = 4. The workers run at normal priority; a host that gives its audio thread real-time priority is safe anyway, but REAPER on Linux without rtkit and many hosts' extra audio workers run at normal priority too, and the player often listens while a hint is computed (Mine ▶ renders live in `process()`). Half the logical CPUs is about the physical cores, so the SMT siblings (at least one whole core on any machine with two or more) stay free for the host's audio, GUI and main threads. More than four does not pay: the parallel batches are 6–20 renders and the verification steps are serial (the table). RAM: a worker holds one render (a few MB) and its describer.

Each round plays one flow, interleaving 1 worker and 4 workers four times each with the order alternating (serial, parallel, parallel, serial, …) so the drifting load falls on both; medians. ## Create (lane SK3, R3)

**With the `create` cargo feature the plugin creates patches from a sound file end to end: the shell decodes the file, `enth-analysis`'s intake conditions it, `enth-solver`'s `create` builds the portfolio and refines K branches, the session's `create` module keeps the read model and turns "Use this" into one undo step** (freeze point F2s, [phase-3.md](phase-3.md); the session's side is [session.md](session.md#create-lane-sk3-r3); the design is [r3.md](r3.md)). Everything is in `src/create.rs` and `src/create/decode.rs`, wired additively behind the feature in `lib.rs`, `process.rs` and `editor.rs`, and the editor's Create view is in `enth-ui`'s `editor/create/` (lane SK3's minimal panel, then lane PUI's view: [editor.md](editor.md#the-create-view-lane-pui)). **`create` is off by default at F2s**; without it the session's create requests are drained and dropped, and nothing is saved either way.

| Part | Thread | What it does |
| --- | --- | --- |
| `Create` (in `Shared`) | whoever drains the session | `Shared::with_session` drains `Session::drain_create_requests` beside the others and hands them to `Create::act` after unlocking: a `Run` is queued for the thread, a `Cancel` drops a queued run (posting its end at once) or raises the running job's flag, auditions go to the thread |
| the create thread | `enth-create`, spawned at the first request, joined when `Shared` drops | one job at a time ([below](#a-job)); a panicking job is posted as failed (the crash hook writes its file) and the thread goes on. Its posts go to a queue behind a short `parking_lot` lock, each asking the open editor for a repaint |
| the job's pool | `enth-search-0` … `enth-search-(n-1)` | `rayon::ThreadPoolBuilder::build_scoped`, so the pool's threads are **joined** when the job ends (a plain `ThreadPool` drop does not wait, and a thread left running in an unloaded plugin crashes the host); `n` = `min(available_parallelism / 2, 8)` (6 on the owner's 12-thread laptop), normal priority. Each thread keeps a scorer (lane OBJ's `RobustWorker`: FFT plans, buffers) |
| the editor glue | GUI, once per frame | the thread's posts back (`Session::create_post`), the session's `CreateView` to the editor before the frame (`Editor::set_create`, which also makes the header show **Create**), the panel's intents to `CreateEdit` after it (`Editor::apply_create`). The view asks for no frames: posts wake the editor |
| `AuditionPlayer` | audio | a candidate rendered at the host's rate, handed over through `AuditionSlot` (an incoming and a retired `AtomicPtr`, as `game::Mailbox`) and added to the block once, from its start. ### A job

1. **Decode** the file ([below](#decoders)), polling the job's cancel flag and the time cap between chunks.
2. **The intake** (`Intake::with_cfg`, with the decoder's codec hint in `IntakeCfg::codec`), then `Target::from_intake` (the scored 3 s window, `RENDER_SEED`); an `Intake` post carries how the file decoded, the report whole and the notes.
3. **The starts:** the heuristic start on the `init` template, the templates (`pluck_1osc`, `pad_2osc`, `bass_sub`, embedded from `content/templates/` as the CLI's are) and, when the bank is found, the k-NN neighbours (`CreateCfg::default()`, K and the render cap from the job's settings).
4. **The search:** each round's merged batch on the pool, distances back by index; a `Round` post after every told round (the progress and the K candidates); auditions asked meanwhile are served between rounds. **The objective is lane OBJ's robust distance** (`logmel-pool85-robust/1`, [r3.md](r3.md#the-robust-objective-lane-obj); lane SK3M switched it on merging main, by the coordinator's word): `RobustMetricTarget::from_intake(&target, &intake.report)`, one `RobustWorker` per pool thread, and the id `create::OBJECTIVE` (= `METRIC_ROBUST`) in the intake post's notes ("objective: logmel-pool85-robust/1"); `enth create`'s `run` does the same and records it as `enth.create/1`'s `settings.objective`. It stays a parameter (`create::Objective`: its id and a scorer per thread; `Objective::metric_v1` keeps metric v1, `logmel-l1/1`, for comparisons).
5. **The end:** a `Done` post with the stop and the final candidates. The job's target stays for auditions until the next job.

**Cancel within one batch.** The job's `AtomicBool` is checked before every render in the pool and after each round; a batch a cancel interrupts is dropped and **never told** (`CreateJob::cancel`), so the result is what the rounds before it found and the run stays a prefix of the full one. **The time cap** (the job's `seconds`, at most 300) is checked the same way, from the job's start: past it the batch is dropped and the job ends `cancelled`, with the note "stopped at the time cap". **Unload never hangs:** `Create`'s drop raises the running job's flag, wakes the thread and joins it; the pool stops within one render per thread and the decoder within one chunk.

**The bank** (`enth-bank-v1.bin`, `cargo xtask bank`) is looked for beside the plugin's binary (`dladdr` on Linux and macOS, `GetModuleHandleExW` and `GetModuleFileNameW` on Windows: the CLAP file's folder, or the folder of the binary inside a VST3 bundle), then in `$ENTH_MODELS_DIR` or `<Documents>/enth/Models/`. A missing or refused bank (`Bank::parse` checks it) means the job runs on the heuristic and the templates, and its notes say so and where it looked. **Shipping it** (lane INTa): a release run with its `create` input on rebuilds the bank on each leg with `cargo xtask bank`, checks its SHA-256 against the pin (`66d5f380…`) and puts `enth-bank-v1.bin` in the zip beside the bundles, never inside one (a file inside a macOS bundle's `Contents/MacOS` breaks its signature); friends put it in `<Documents>/enth/Models/` or, on Windows and Linux, beside the `.clap` file ([distribution.md](distribution.md#create-from-sound-in-a-build-r3a-lane-inta), [friends-install.md](friends-install.md)). Owner build 5 copies it to `~/Documents/enth/Models/` ([owner sheet 5](r3-owner.md)).

### Decoders

`src/create/decode.rs`, shared with `enth create` (the CLI includes the file by path), so both shells decode a file to the same bits:

| Format | Crate | Exact? |
| --- | --- | --- |
| WAV (8–32-bit integer, 32-bit float) | `hound` | yes: integers scaled by a power of two |
| FLAC | `claxon` | yes (the fixture decodes to exactly the WAV's samples) |
| Ogg Vorbis | `lewton` | the same bits twice on one machine; **across platforms unverified**, and unlikely: its window and twiddle tables use std's `sin`, `cos` and `exp` |
| MP3 (MP2, MP1) | `nanomp3` (a port of the CC0 minimp3) | the same bits twice on one machine; across platforms unverified (it keeps C's evaluation order and uses tables, no std transcendentals, and its default `wide` SIMD path runs the same lane arithmetic) |
| AIFF and AIFF-C (lane INTa, 2026-10-22) | our own reader, no dependency | yes: integers scaled by a power of two of their container, so a 16-bit AIFF gives the same bits as the same samples in a WAV (tested against `tone.wav`) |

- At most 60 s are read (the intake looks at 30 s from a second before the first sound); M4A/AAC (`symphonia`, MPL-2.0) waits for the owner's OK.
- **AIFF** (lane INTa): a `FORM` of chunks in any order, padded to even lengths; `COMM`'s 80-bit extended rate (exact powers of two, rounded to the nearest hertz) and, in AIFF-C, the compression type; `SSND`'s offset. Read: big-endian integers of 1–32 bits (AIFF, AIFF-C `NONE` and `twos`), little-endian ones (`sowt`) and big-endian floats (`fl32`, `fl64`); any other compression (`ulaw`, `ima4` …) is refused as `unknown_format` with a hint. A file that ends inside its samples keeps its whole frames; an `SSND` size a writer never filled in reads to the end; the header alone never sizes an allocation. Tests build their files in the test (`decode.rs`, `tests_create.rs`'s `aiff_and_aiff_c_decode_to_exactly_the_wavs_samples`), so no AIFF fixture is committed.
- **192 kHz and above are decimated exactly 2:1** (again while still 192 kHz or more: 384 kHz → 96 kHz, 352.8 kHz → 176.4 kHz) by a fixed 63-tap half-band FIR (Kaiser β 9; flat to 40 kHz at 192 kHz, −61 dB at 56 kHz, below −100 dB from 60 kHz), summed in `f64` in a fixed order; the note says so. Other rates outside the analysis's 8,000–191,999 Hz are refused (`sample_rate`), and the hint says both.
- **The codec hint** (`IntakeCfg::codec`: the codec, lossy or not, the bitrate when the stream says): with a lossy hint the intake's bandwidth estimate accepts an edge with two partials in the octave under it instead of three, so a high note's sparse spectrum no longer hides an encoder's low-pass (the A7 fixture at 48 kbps: no cut-off without the hint, 11.2 kHz with it). Absent, nothing changes; the report records it.
- Every result records the scored clip's hash (`enth.create/1`'s `input.audio_sha256`), so a replay can check its clip.

## Duels (lane SKD, R5a)

**With the `duel` cargo feature the plugin plays async duels end to end: the duel card shares a passed round as a scorecard and an answer code, reads a friend's whole chat message, keeps their answer sealed until you have played, checks it on this computer and loads it as one undo step** (freeze point F2d, [phase-4.md](phase-4.md); the codes are [challenge.md](challenge.md#version-15-the-kinds-behind-the-escape-r4-r5)'s, the duel state is [session.md](session.md#duel-lane-se-r5a)'s, the design is [duels.md](duels.md)). Everything is in `src/duel.rs`, wired additively behind the feature in `game.rs` (`Msg::Task`, `Game::run_task`, the `Game::duel` field), `lib.rs` (the duel requests drained in `with_session`) and `editor.rs` (the hooks get `game`); the card is `enth-ui`'s `editor/duel/` (lane SKD's minimal card, then lane DUI's). **`duel` is off by default at F2d**: lane DUI's card and INT5's friend build decide when it turns on. Without it the session's duel requests are drained and dropped; nothing is saved in the project either way. **No networking code.**

| Part | Thread | What it does |
| --- | --- | --- |
| `Duel` (in `game::Game`) | whoever drains the session | the duels' salts and codes, the worker's posts, what the shell last said; `Duel::act` (after unlocking, every drain) sends the tasks queued under the lock to the worker and acts on the session's `DuelRequest`s: `Verify` to the worker, `Cancel` skips a job that has not run, `Audition` and `StopAudition` |
| the game worker | `enth-game` (lane SKR's thread) | `WorkerTask`s, run with the worker's `Runner` and the host's rate, after the jobs queued before them; a panic is caught and posted as a failure. The worker asks the editor for a repaint after each |
| the editor glue | GUI, once per frame | before the frame (`duel::before_frame`): the worker's posts back (a verify result through `Session::duel_job_done`, codes kept with their duel), a refused audition stopped, then the session's `DuelView` and the shell's codes to the card (`Editor::set_duel`); after it (`duel::after_frame`): the card's intents applied (`Editor::apply_duel`), and **Share** taken (`Editor::take_duel_share`) |

**Share** (the card's click): the player's result is cloned on the click (`DuelEdit::duel_own`; refused with a reason when it cannot be shared: nothing submitted, not settled, revealed), a duel is opened on its code if none is, the **salt** is drawn, then on the worker: `AnswerCode::new(challenge, salt, &patch)` → the round prepared once with the round's own frozen scorer set (`verify::prepare`) → the **canonical answer** scored (`score_round(&round, answer.answer())`) → `Scorecard::new(…, answer.commitment())` with the compared submit's number, the time (to the pass, else the round's active time) and the assists; the share message is the scorecard's two human lines and the scorecard. The claim is the canonical answer's score, because that is what any receiver re-scores: on the same engine a check reads "as reported" (a claim rounded from the session's hundredths could read one tenth off). About a second; the codes come back with the next frame.

**The salt** (the F1e review's M6): 64 bits of OS randomness, `getrandom::u64` (`getrandom.workspace`, optional behind `duel`), drawn **once per duel** at its first Share and kept with the duel's codes before anything can be copied; a second Share gives the same codes. **Never a clock or a seed**; without OS randomness no codes are made. The salt lives as long as the plugin instance until lane DUI writes it to the duel history with the codes.

**Verify** (the session's `DuelRequest::Verify`, on the worker, the F1e report's order): their answer decoded (`AnswerCode::decode`: the challenge regenerated, the ops applied, the tail checked) and their scorecard; an answer for another challenge than the duel's fails as `not_the_same_challenge`; the round prepared **once** with `verify::scorer_set(card)`; `verify::verify_prepared` on theirs; your patch re-scored on the same round as its canonical answer (`AnswerCode::new` with a salt that is never shown: the salt plays no part in the canonical answer); posted as `DuelVerified::new(own, theirs).with_patch(their answer).with_claim(v.claim)`, re-scores in the session's hundredths. A refusal (`answer_too_new`, `bad_check`, `answer_mismatch`, `target_mismatch`) is the job's `Failed` with its code and hint. About two seconds in REAPER.

**Audition**: their patch rendered with the challenge's phrase (`random::target`'s) at the host's rate and played through the Learn examples slot as a set of one example at 0 dB (the `learn` feature; on by default), looping until Stop; **no new audio-thread code**. Refused while a round's target holds that slot (end the round first), and without `learn`: the shell says why and stops it in the session.

**The clipboard** is the card's, never this file's: egui's `copy_text` inside a click on Copy writes it; a paste is the platform's Paste (Ctrl+V, ⌘V) into the paste box, which the vendored egui-baseview turns into text (with fork patch 4, the box takes the keyboard only while it is focused). Nothing reads the clipboard otherwise.

**The duel log** (`ENTH_DUEL_LOG`, a file path; unset by default): one JSON line (`enth.duel-log/1`) per share (the codes and their sizes) and per change of the duel's state (the answer `none`/`sealed`/`open`, the check's state and what it measured), codes and scores only. It is the REAPER `duel` scenario's window into the card, not the history.

**Measured** (2026-10-22, debug bundles): the REAPER `duel` scenario 15 of 15 on CLAP and VST3 (21.8 and 19.9 s at load 2–4; the codes in 0.4–1.1 s, the check in 0.4–1.9 s, the slower figures at load 11–15); the whole suite on the `duel` bundle 351 of 351, and on the default bundle 321 of 321; `validate` 36 passed, 0 failed, 8 skipped on both bundles; `host-render` exit 0. `leak-test`: the default bundle 14.06 KB per cycle, the `editor-counts,duel` release bundle (the opener drawn every open) 19.07 KB per cycle (limit 26), 3 threads after every close, 200 of 200 first frames twice, churn 0.35–0.48 KB per cycle. `cargo xtask bundle enth-plugin --features rt-stats` (the bundler passes cargo options through) compiles `rt_stats.rs`: `process_block` reads `Instant::now()` at its top and records the elapsed time at its end (the plugin's own work, nice-plug's wrapper excluded) into a log-scale histogram of atomic counters, 16 buckets per octave of nanoseconds (each at most 6.25 % wide), plus the count, frames, sum and maximum: relaxed atomic adds, no lock, no allocation. `Shared::rt_stats.snapshot()` gives p50, p99, p99.9 (the upper edge of the bucket that holds them, so at most one bucket high) and the maximum; at `deactivate`, if `ENTH_RT_STATS` names a file, one JSON line (`enth.plugin-rt-stats/1`, microseconds, with the non-empty buckets) is appended and the counters restart. Without the feature the module is not compiled and `process()` reads no clock. It complements `enth-test-host process-stats`, which times the whole `process()` call from the host's side. ## Determinism

A plugin render equals `enth render` when the sample rate matches, the engine was not re-activated or reset during the render, no plan swap, monitor bypass or audition note happened, and every event is one a `Performance` can express (notes, slot automation, macros and the mod wheel). The shell keeps its side: `SAMPLE_ACCURATE_AUTOMATION = true`, `RENDER_SEED` (the CLI's default), no echo of host values at activate, slot events resolved by the engine with the patch-wins equality rule, `reset` equal to a fresh engine, the `patch` field carried as text, events never dropped (chunks), and a zero-length note ordered like the CLI's.

Measured at PL (2026-10-20):

- `enth-test-host cli-equal` (debug and release bundles): **63 of 63** engine golden cases equal through the plugin at host blocks 1, 64, 100 and 4096, `mod-controls` included (its macros as host parameters, its mod wheel as MIDI CC 1); 10 are skipped by the test host (render seeds other than the default, the stand-in sine, engine-address automation that needs a profile).
- In-process (`tests_host.rs`), bit for bit against `enth_render`: slot automation (the CLI automates the target with `from_norm` of the host value), macro moves and the mod wheel (`controls`) at host blocks 1, 64, 100 and 4096; the monitor bypass against the patch without its reverb; a zero-length note; the rest of a render after a reset against a fresh render; a reactivation.

## RealtimeSanitizer (lane INT, R1/S1)

`cargo xtask rtsan` (`xtask/src/rtsan.rs`) runs the whole plugin's `process()` under RTSan in the test host, where the nightly workflow covers only the engine's and render's own tests. Both binaries are built with a nightly toolchain and `-Zsanitizer=realtime --cfg enth_rtsan -C link-arg=-Wl,--export-dynamic` into `target/rtsan/`: `--cfg enth_rtsan` marks nice-plug's CLAP `process` entry (the vendored fork's patch 10, so the wrapper's own event handling is covered too), `Plugin::process` and `Engine::process` `#[sanitize(realtime = "nonblocking")]`, and the test host links the runtime and exports it so the plugin's calls resolve. Any allocation, lock or blocking call inside `process()`, the host's callbacks included, aborts the run (exit 43) with its stack, which the command names from the binaries' symbol tables. The runtime intercepts `malloc` and its family, the pthread locks and condition variables, I/O and `syscall` (so a contended std lock or a thread wake-up, both `futex` calls, is caught), but not `pthread_self`. No system package: the runtime ships in the nightly `rust-std`.

The other scenarios run with the test host offering CLAP's thread-check extension (`ENTH_TEST_HOST_THREAD_CHECK=1`, as REAPER and Bitwig do; off by default so the other gates keep the host they were measured with). Findings:

- **A host without thread-check got an allocation on the audio thread** (lane INT), at the first GUI task `process()` scheduled on a thread: a voice-count change (step 7 of [the audio block](#the-audio-block), `set_current_voice_capacity`) or a parameter change (nice-plug tells the editor). nice-plug's `schedule_gui` asks `is_main_thread`, whose fallback was `std::thread::current().id()` under `permit_alloc` (its FIXME, which is why `assert_process_allocs` never saw it). The stack showed the cause: `std::thread::current` → `__tls_get_addr` → `malloc`, glibc creating the plugin's thread-local block for that thread (a `dlopen`ed library gets it lazily, under the loader's TLS lock). **Fixed by fork patch 10** (FU1 lane FK, `vendor/README.md`): the fallback compares the OS thread identity (`pthread_self`, `GetCurrentThreadId`; `pthread_main_np` in the macOS event loop), which touches no thread-local storage. The proof is the two `no-thread-check` rows; on the tree before the patch (`5e394e4`) both abort with exit 43, `std::thread::current` in the stack, through `Enth::process_block` and through `Wrapper::handle_in_events_until` → `update_plain_value_by_hash`. The same fallback served the VST3 wrapper in every host (its `schedule_gui` asks the OS event loop), so VST3 parameter changes inside `process()` no longer pay for it either.
- **The test host allocated in the plugin's real-time context** in `bursts`: its 64-event output buffer grew while the plugin pushed `NOTE_END`s (the host's `try_push`, a `realloc`). Fixed: 8,192 events reserved (`OUTPUT_EVENT_CAPACITY`). Real hosts preallocate.

**Not covered** (open; FU1 lane FK's audit of nice-plug's `schedule_gui` callers):

- **The background pump.** `execute_background` (step 6, [the pump](#the-pump)) is a bounded crossbeam `try_send` to nice-plug's worker. When the worker is waiting, which is its idle state, the send takes the channel's std mutex, calls crossbeam's `current_thread_id()` (a `thread_local!` filled from `std::thread::current()`: the allocation patch 10 removed, once per audio thread) and wakes the worker (a `futex` call, which RTSan intercepts). No scenario reaches it: a compile stays pending only while two plans are in flight (the host stopped calling `process()`), which none of them produces, so RTSan has not seen it. ADR-0001's note of 2026-10-19 accepted the wake-up and says when to revisit. A fix is a design change (the worker polls a lock-free queue, or the pump goes through CLAP's `request_callback`), not a thread-id patch.
- **The VST3 wrapper**, which the test host cannot load. Off the main thread its `schedule_gui` reads the editor's `RwLock` (`plug_view`) while the editor is open, and otherwise queues to the OS event loop; on Linux that loop's queue is the same background worker, so each parameter change inside `process()` with the editor closed costs the pump's `try_send` above. Windows and macOS queue to the GUI thread's channel, whose receiver never waits (no lock, no thread id) and then post a message (`PostMessageA`, `CFRunLoopSourceSignal`).

About 5 minutes to build cold and a minute to run (`--secs` per `process-stats` scenario, default 10). A local check, not in CI; the nightly workflow could run it next to its RTSan job.

**How a scenario loads a patch.** `inject_state(track, fx, var)` in `common.lua` writes a state chunk into REAPER's `clap_chunk` / `vst_chunk` named config parameter. The chunk is built by `write_state_chunk` (`xtask/src/reaper/chunk.rs`) from a fixture and handed to the script through an environment variable. Layouts measured on REAPER 7.82: CLAP is a `u64` length and then the JSON; VST3 is a `u32` length, a `u32` 1, the JSON and 8 zero bytes. The JSON is nice-plug's `{"version","params":{id:{"f32":v}},"fields":{"patch":"<text>","enth":"<text>"}}` and the `patch` field is exactly `Patch::to_json()`, so a saved state is compared with `Saved::patch_text` byte for byte. `dump_chunk` in the Lua helpers prints a chunk for debugging.

**Robustness rules** (each came from a flake):

- Poll, do not sleep: `wait_until(pred, timeout, step, fn)` waits for a condition. `show_editor` waits up to 15 s for the window to be viewable and to draw.
- Raise the X window before reading pixels. Under Xvfb there is no window manager, so REAPER's main window can cover the plugin window and `XGetImage` returns the covering window's pixels. `xinput.py stats` raises it first. `xinput.py` (find, client, raise, click, drag, key, stats) refuses a real display: `DISPLAY` must be `:50` or higher, as `xvfb-run -a` gives.
- Offline render is not a golden. Renders are 32 short notes repeated every 0.125 s and the analysis uses per-note medians over the even-pitch notes (roughness is bimodal by pitch) and allows at most two outlier notes. Audio checks are directional (brighter, louder, steadier), with margins measured on both formats. The note that REAPER's `-renderproject` used to drop on CLAP was nice-plug's restart on the render-mode switch, honoured about 30 ms of wall-clock time into the render, at an audio time that depended on the render's speed; with the fork's patch 9 the plugin is not restarted and two renders of a project are the same from 0.25 s on (`render-repeatable`), which is how a return of the restart shows. The first note may still start differently after REAPER's pre-roll (2 of 8 renders), so the first two notes stay unmeasured.
- Logs are named `{format}-{scenario}-{phase}` and the report scope is `{format}/{scenario}`; two renders sharing one append-mode log once mixed their lines.
- **REAPER also scans the standard `~/.vst3` (and `~/.clap`)**, besides the sandbox's plugin path. With an enth installed there (`cargo xtask install`, an owner build) the VST3 runs loaded the installed build instead of the bundle under test (lane SKD, 2026-10-22: a `create` build installed at 15:55 had no `duel` card, so `vst3/duel` failed while `clap/duel` passed). The `duel` scenario runs REAPER with `HOME` set to an empty folder in its results; the other scenarios still use the real home, so their VST3 rows test an installed build whenever one exists. With `HOME` isolated for every launch (a local, uncommitted check), the default suite passed 321 of 321 and the `duel` bundle's 351 of 351.

**The open check: does an editor-only edit mark the project dirty? It did not (RH); it does now (FK2).** `dirty-flag` opens the editor, finds a knob with a click-and-drag search (first try at editor point (366, 178), osc1's "Level" knob in the "lanes" layout, then a grid; the `ENTH_EDIT_POINT` environment variable overrides it), edits the patch, and reads `IsProjectDirty` at once, about 3 s later and after the window closes. With the fork's patch 6 ([Dirty marking](#dirty-marking)) it reads 1 at once and 3 s later on both formats, and `DIRTY_MARKING_EXPECTED = true` in `reaper.rs` makes a clean project after the edit a failure; `clean-without-an-edit` (the idle phase, the editor open and nothing edited) must read 0, so a plugin that marked the project dirty on every frame fails too. The control edits a slot-bound knob, which moves a host parameter and reads 1. ## Leak gates

`cargo xtask leak-test` (lane INT; `xtask/src/leak.rs`) runs the two leak gates of [phase-1b.md](phase-1b.md#the-plugin-side-g1-checks) under an Xvfb it starts itself (`xvfb-run -a`, no display variable passed on), before merging an editor lane and nightly (CI job `leak` in `nightly.yml`):

- **`editor-cycles`**: `enth-test-host editor-cycles` with 200 open/close cycles, twice, each against the no-editor baseline in its own process. Passes when the anonymous footprint's growth after close (`Pss_Anon + SwapPss`; the worst editor run's slope after 10 warm-up cycles, minus the baseline's mean) is at most 26 KB per cycle, the thread count after every close (once threads that are still exiting are gone) is one value, every open draws its first frame in time, and the plugin counted one `editor_closed` call per `build()` and one build per cycle.
- **`churn`**: `enth-test-host churn` with 200 instance lives on `tools/test-host/golden/enth-plugin.patch.json`; the test host's limits (1 KB per cycle, no thread or descriptor left behind) and its exit status decide. PSS is sampled after `malloc_trim(0)` (below).

The host cannot see `editor_closed` (the fork's patch 2), so the gate builds the release bundle with the plugin's `editor-counts` cargo feature (`src/editor_counts.rs`): `build()` and `editor_closed()` each add one to a relaxed atomic, and when the last reference to `Shared` goes (the plugin and every editor are gone) the counts are appended to the file `$ENTH_EDITOR_COUNTS` names (`enth.plugin-editor-counts/1`). **Frames** (lane AM, additive fields): every drawn frame counts (`frames`), and a frame that follows one which asked for a repaint (visible live data was changing) is a live frame, the time since its predecessor live time, so `live_fps` (`live_frames` over `live_ms`) is the rate the window really got while it animated, idle time not diluting it. `leak-test` reports them per instance (`plugin_frames` in `leak-test.json`; no check reads them): measured under its Xvfb, 965 and 992 frames over the 200 cycles, a live rate of 26.0 and 27.8 fps with the editor's 1/60 s request, against 23.0 and 23.8 fps with the old 1/30 s request (a control build). **Owner check 1.3** reads them on the real display: install with `cargo xtask install --package enth-plugin --release --features editor-counts` (the options go through to cargo), start REAPER with `ENTH_EDITOR_COUNTS=$HOME/enth-counts.jsonl`, play with the editor open, then quit REAPER (the line is written when the plugin goes); the editor asks for 1/60 s, which should give about 30 live frames a second under baseview 0.4.1. Without the feature nothing is counted. The bundle is copied to `target/leak-test/` with the reports (`editor-cycles.json`, `editor-counts.jsonl`, `churn.json`, `leak-test.json`); `--bundle-dir`, `--only editor|churn`, `--cycles` and `--repeat` exist for experiments, but the gate is 200 cycles: over 30 cycles the warm-up dominates the slope (the shipped bundle read 28.8 KB per cycle at 30 and 12.4 at 200).

Measured on INT's branch (2026-10-20, load 13–16, 3 min 9 s): 12.31 and 12.45 KB per cycle (baseline 0.0), 3 threads after every close, 200 of 200 drawn, (200, 200) counts in both runs; churn 0.54 KB per cycle, +0 threads, +0 descriptors. Control: the `0f4f29d` bundle, built without the feature, fails the counts check (exit 1).

**Repeatable numbers** (lane LK, R1/S1, 2026-10-20). The gate turned flaky on main: one editor run of two read 53.05, then 53.51 KB per cycle, and once the threads read [3, 4]. None of it was a leak; the measurement depended on the allocator, on swapping and on Mesa's teardown timing:

| Symptom | Cause (found with `ENTH_LEAK_DIAG=1`, below) | What the gate does now |
|---|---|---|

**Software GL under Xvfb** (lane NTF, FU1). The editor's baseview opens its GL context through EGL, else through GLX with an sRGB framebuffer config, and Xvfb (21.1.12 with Mesa 25.2.8) offers sRGB GLX configs only when the server itself can load Mesa's EGL vendor. So a machine needs `libegl1` and `libegl-mesa0` besides `libgl1-mesa-dri` and `libglx-mesa0`; without them every `gui.create` fails, the plugin counts no build and nothing is drawn (the first nightly, run 39506542786; reproduced by hiding the vendor with `__EGL_VENDOR_LIBRARY_FILENAMES=/nonexistent.json`). `leak-test` then says so in its counts and drawn checks, with the plugin's first log line. The nightly job installs both and prints `eglinfo -B -p x11` and `glxinfo -B` under Xvfb.

**Transparent huge pages** (lane NTF, FU1). With the editor open on the runner, the gate read 2052 and 2062 KB per cycle against about 13 here: steps of exactly 2048 KB per open, not per frame. The runner's kernel has THP `always` (`max_ptes_none` 511; this machine has `madvise`). `ENTH_LEAK_DIAG` showed the step: each open on the EGL path maps a new 10 MB executable region (llvmpipe's JIT code) and keeps it after the close. With 4 KB pages about 8 KB of it is touched per open, part of the residual above; under THP `always` the first touch brings in a whole 2 MB page. The same editor on the GLX path (EGL hidden from the test host only) keeps one such region for the whole run. baseview's EGL teardown is in order (gdb: `eglDestroySurface`, `eglDestroyContext`, `eglTerminate`, `XCloseDisplay`, each succeeding, on the window thread), and a bare EGL loop with a fresh display, an sRGB surface, a 3.2 core context, a texture and a shader per cycle, on a thread per cycle, does not grow either. So the region comes from Mesa's EGL and llvmpipe teardown under something egui's renderer does; which call is open. It costs nothing on a GPU driver (llvmpipe runs only without one). The measurement processes (`editor-cycles`, `churn`) now turn THP off for themselves (`prctl(PR_SET_THP_DISABLE)`, inherited by the processes they start; reported as `thp`, kept with `--system-thp`). Same runner, THP off: 20.58 KB per cycle over 60 cycles; here 12.91 over 200. `leak-test` prints each run's steps, frames and threads when an editor check fails, and the nightly's `leak_diag` dispatch input sets `ENTH_LEAK_DIAG`.

## Soak

`cargo xtask reaper-soak --minutes N [--bundle-dir D]` (lane SOAK; `xtask/src/reaper/soak.rs`, the driver `xtask/reaper/soak.lua`) is the long run behind gate GS1, "no crashes or audio-thread allocations under clap-validator and a one-hour REAPER soak". A local gate, not CI; `--minutes` defaults to 60. It builds the **debug** bundle (`--no-build` reuses `target/bundled`; `--bundle-dir` takes a copy), so nice-plug's `assert_process_allocs` aborts the process on any allocation in `process()`, and runs the native REAPER of `reaper-test` (a private copy, a fresh `reaper.ini`, Dummy Audio at 48 kHz) under `xvfb-run`, never on the real display. The transport does not run under Dummy Audio, so every note goes through REAPER's virtual keyboard (`I_RECINPUT = 4096 + (63 << 5) + channel`, `I_RECMON`, `I_RECARM`, `StuffMIDIMessage`), one track and one instance per MIDI channel (`--instances`, 1 to 16, default 4).

What the script does for the whole time:

| Action | How often | Detail |
|---|---|---|
| Notes | all the time | four patterns on the four channels: a chord every 0.5 s; a run of single notes every 0.12 s; a burst of 24 notes in 0.5 s every 12 s (more than the 16 voices, so voices are stolen), held 3 s; three held notes for 6 s with CC 1, pitch bend and the sustain pedal moving, every seventh round ended by CC 123. `--no-notes` turns them off |
| Sweeps | every tick of 50 ms (about 57 parameter sets a second per instance) | every parameter of every instance follows its own slow sine (the 8 macros 0.05 to 0.5 Hz, the slots 0.02 to 0.2 Hz, random phase), 2 macros and 2 slots per instance per tick; one set in 300 jumps to 0 or 1. `--no-sweeps` |
| State loads | `--load-secs`, default 90 | `clap_chunk` (or `vst_chunk`) on one instance in turn, from seven patches built by `chunk::write_state_chunk`: roundtrip, starter, state, slot, macro, wheel, dirty-control |
| Instance churn | `--churn-secs`, default 300 | delete the plugin and add it again on one track, then load a patch; every fourth churn with the editor open (the window must go with it) |
| Editor | `--editor-secs`, default 60 | open the floating window, wait for the first drawn frame, drag the osc1 Level knob with real X events (`xinput.py`), hold `--editor-hold-secs` (5), close, wait for the window to go, settle 3 s, read the memory. `0` never opens it |

The xtask supervises REAPER from outside: it finds the process by its executable, samples `smaps_rollup` every `--sample-secs` (15) (`Pss`, `Pss_Anon`, `Pss_File`, `SwapPss`, `Rss`), the thread and descriptor counts and the Xvfb server's PSS, and reads the script's log (`soak.log`: `check` and `data` lines). Checks, all of which must pass for exit 0:

| Check | Fails when |
|---|---|
| `no-allocation-abort` | REAPER's output has "memory allocation of N bytes failed" (the allocator's error handler after `assert_process_allocs`; exit 134) |
| `no-crash` | REAPER is gone before the script's `finished` line, or exits non-zero (the signal is named) |
| `no-hang` | no new line in `soak.log` for `--hang-secs` (90; 240 s while REAPER starts); the threads' states are read from `/proc` first (gdb cannot attach under Yama), then the group is killed |
| `ran-to-the-end` | the script stops short of `--minutes` |
| `allocation-guard-armed` | the bundle does not carry `nice_assert_no_alloc` (not a debug build) |
| `load-N`, `host-calls-ok` | an instance does not load; a state load, parameter set or churn is refused by REAPER |
| `editor-cycles-drew-and-closed` | a cycle draws no first frame or leaves its window behind |
| `tracks-stay-unmuted` | a track gets muted behind the script's back (see Gotchas) |
| `instances-keep-sounding`, `audio-flows` | an instance makes no sound for 5 whole minutes in a row, or never |
| `memory-growth` | the anonymous memory (`Pss_Anon + SwapPss`; a Theil-Sen slope over the settled samples, editor closed for 5 s, after the warm-up of 25 % of the run clamped to 60 to 600 s) grows more than `--max-pss-mb-per-hour` (5.0); the file-backed PSS and the Xvfb's are reported beside it. Fewer than 8 settled samples is a fail for runs of 30 minutes or more, a note below |
| `threads-steady` | the settled thread counts differ by more than `--max-thread-spread` (2) |
| `fds-steady` | the descriptors at the end exceed those at the start by more than `--max-fd-growth` (4) |

`editor-cycle-growth` is information only (the per-cycle slope after the warm-up, the median cycle, the test host's gate for comparison), as are `underruns` (Dummy Audio has no deadline) and `audio-coverage`. The report `soak-report.json` (`enth.reaper-soak/1`; `--report FILE` copies it) holds the commit, verdict, failed checks, config, limits, how the run ended, the fits, all checks, every sample, every editor cycle (memory before and after), the per-minute peak of each instance and the script's events; a short text summary goes to stdout. `--self-test crash|hang` signals REAPER 30 s in: the run must fail as `no-crash` (SIGSEGV) or `no-hang`.

Negative control for the allocation guard: a temporary `Vec::with_capacity(48)` in `process_block` after 3000 blocks, built as a debug bundle (never committed), aborts REAPER with "memory allocation of 48 bytes failed" (exit 134) and the soak fails `no-allocation-abort` with that message, so the guard is armed under REAPER.

Measured on SOAK's branch (2026-10-20, commit `08ebb00`, debug bundle, 4 instances, defaults, 60.1 min wall clock under `flock -s`): **exit 0, all checks pass**. 62192 notes, 55710 controller moves, 822944 parameter sets (0 refused), 54 state loads (0 failed), 11 instance churns (0 failed, 2 of them with the editor open), 60 editor cycles (60 drew, 60 closed, 60 of 60 XTest edits changed the patch); every instance sounded in 59 of 59 whole minutes (peaks 9.9 to 11.8 per instance); no allocation abort, no crash, no hang. Anonymous memory (`Pss_Anon + SwapPss`) 81 MB at the start, 152 MB at the end, **+1.7 MB/h** over 160 settled samples after the 600 s warm-up (limit 5.0); the threads read 27 in every settled sample, the descriptors 9 at both ends; the editor cycles read +12 KB for the median cycle and +31 KB per cycle by the slope over 50 cycles (noisy; the 10 s cycles below are the better number). Control runs of the harness itself: `--self-test crash` fails `no-crash`, `--self-test hang` fails `no-hang`, and the allocation negative control fails `no-allocation-abort`. The report of that run is `enth.reaper-soak/1` JSON (`soak-60min.json` in the lane's scratch).

### Gotchas

- **REAPER's circuit breaker mutes loud tracks.** Preferences > Audio has "Automute: track output exceeds" (`automute=2`, level `automuteval=8.0`, linear, +18 dB, by default), and REAPER neither plays nor processes a muted track. A burst of 24 notes through a patch with no limiter peaks at 8 to 40, so within seconds one instance after another went silent and stayed silent, which looked like a plugin bug (it was the same with the stock ReaSynth). The soak's `reaper.ini` carries `automute=0` (`automuteflags=0` does not help), the script logs every `B_MUTE` change with the last 48 MIDI messages, and the `tracks-stay-unmuted` and `instances-keep-sounding` checks fail a run that goes silent again.
- **The Bash tool of the agent harness caps a foreground command at 10 minutes.** An hour has to run detached (`setsid nohup … &` under `flock -s /tmp/enth-quiet.lock`) and be polled with `until [ -f done ] || [ $SECONDS -ge 480 ]; do sleep 10; done`. If you kill it, end `xvfb-run` with SIGTERM (it ends its Xvfb); an orphaned Xvfb keeps the shared lock and blocks every exclusive timing run. The xtask ends its own Xvfb when the run ends.
- **PSS alone is a bad metric on a loaded box**: page-cache eviction and swapping move it by tens of MB. The soak fits `Pss_Anon + SwapPss`.
- **The editor makes 27 threads 54**: llvmpipe's rasterizer workers, one set per GL context, gone on close. Thread and memory samples are taken only when the editor has been closed for 5 s (`mark` lines in the log).
- `gdb` cannot attach (Yama `ptrace_scope`) and heaptrack segfaults once a plugin opens a window; `valgrind` was not needed.

### Memory per editor open/close

Report 04's 3-minute probe saw 0.5 to 0.7 MB per open/close cycle in REAPER, against 12.4 KB per cycle in the test host's leak gate. Measured here (debug bundle, Xvfb, one instance, a cycle every 10 s; `scratch/exp/*.json`):

| Run | Result |
|---|---|
| `enth-test-host editor-cycles`, 60 cycles | anonymous 36.9, 56.4, 64.5, 65.2, 65.6 MB over the first five cycles, then 14.5 KB per cycle: a **warm-up of about 65 MB** (the plugin's first window, Mesa's GL and llvmpipe's JIT), in the test host too |
| enth in REAPER, 70 min, 418 cycles | 108.7 MB after cycle 1, 147.5 after cycle 5 (the same warm-up), then 15.7 KB per cycle over cycles 6 to 100 and 14.8 over 100 to 200; after that one 11 MB block comes and goes (cycles 197 to 220 flip between 144 and 155 MB) and the memory steps up by 11.9 MB at cycle 327 and 3.8 MB at cycle 370; 168 MB at the end |
| REAPER's own FX windows (ReaEQ, ReaSynth), 90 cycles | flat (0 kB per cycle), no warm-up |
| enth, notes and sweeps, no editor, 20 min | +0.3 MB/h |

So the difference is not REAPER's FX windows or SWELL (the controls are flat), and not a per-cycle cost of 0.5 MB: it is the one-time warm-up of the first few windows (GL, Mesa, llvmpipe, the plugin), which a probe of a few minutes reads as growth. The steady cost is about 15 KB per cycle in REAPER and in the test host alike (the leak gate measures 12.4 KB), independent of llvmpipe's threads and JIT (`LP_NUM_THREADS=0` and softpipe read 20 to 25 KB per cycle on 29 to 40 cycles, noisy). It does not plateau to zero: a linear tail of about 15 KB per cycle (0.9 MB/h at the soak's cycle a minute) plus a few retained blocks of 4 to 12 MB, which look like allocator hysteresis (an 11.1 MB block that is kept in some cycles and returned in the next). The soak's limit (5 MB/h of anonymous memory, the editor cycling once a minute) sits above that tail and below a real leak: 100 KB per cycle would be 6 MB/h and fail.

## Presets

`content/presets/*.patch.json` are sounds made in the editor, each the `patch` field the plugin saved, as `Patch::to_json()` ([content/presets/README.md](../content/presets/README.md)). `cargo xtask extract-presets <project.rpp>...` (lane INT, `xtask/src/preset.rs`) finds every enth instance in a REAPER project, decodes its state with the harness's chunk code and writes the `patch` field with only its metadata changed: the file and `meta.name` come from the FX's own name or the track (`bass` gives `bass.patch.json` named "Bass"), and a sound made from Init loses Init's `init` tag and description and gains the type its name spells (R1/S1 lane INT; before, every sound made from the starter project was named "Init" and collided with the factory Init). A name another preset in the folder already has is refused. `cargo xtask starter-project --out FILE.rpp` writes the project owner build 2 starts from: four named tracks, each holding the CLAP with Init (`content/presets/init.patch.json`, every P1 module, the extra ones switched off, gain-staged; lane AM), the patch a fresh instance plays. `tests/presets.rs` checks every preset, folders included, against the format and the tag vocabulary ([presets.md](presets.md)); `reaper-test` checks both commands against REAPER (`preset-extracted`, `starter-project`).

## Known pitfalls

- **Voice ends.** `Engine::reset` reports no `NOTE_END`, the engine reports at most 256 ends per call, and in mono a voice's key changes under it: the [ledger](#note_end) covers all three.
- **Re-baseline on load.** Values the host restores with a state must not override the loaded patch. Three pieces: the session's first fold after a load only records (so the field folds the restored values right after `load_patch`, or a host change before the next save would be taken as the baseline and lost; the REAPER run found exactly that), the loaded plan forgets the engine's remembered slot values, and `process()` adopts exactly the restored values without sending them (`rebaseline` with `Restored`, set before the plan goes out; `activate` clears it, since it re-baselines anyway, so a change in the first block still counts). A host change after the load is never adopted.
- **The patch wins at activation too.** Host values set before `activate` without a state are recorded, not folded: the engine plays the patch until the host moves a value.
- **Script names after a rename.** A host or script that finds parameters by name sees "Filter 1 · Cutoff" after a load, not "Slot 1". Ids never change; find parameters by id.
- **VST3.** The same code and the same state JSON. nice-plug drops `NOTE_END` and poly-mod for VST3, and voice info is CLAP's. REAPER reads VST3 titles live, so the renamed names show at once (above). The mod wheel arrives through the MIDI CC parameter of its channel (16 in all, CC 1 only; the fork's patch 7). A parameter set from the GUI while the host processes reaches the plugin through `process()`, and REAPER applies a script-set VST3 value only at the next process cycle. `ParamSetter` calls `IComponentHandler` on baseview's thread (F1b decision 3; RH's `slot-automation` scenario passes on both formats, but write and touch modes from the editor are not driven there).
- **Dirty marking needs the fork.** Stock nice-plug never calls CLAP `mark_dirty` or VST3 `setDirty`, so an editor-only edit left REAPER's project clean (RH's `dirty-flag`). The fork's patch 6 adds `HostRequests::mark_dirty`, and the shell calls it on `ShellRequest::PatchEdited` ([Dirty marking](#dirty-marking)).
- **Offline renders in a CLAP host.** Stock nice-plug restarts the plugin when the host switches it to offline rendering, and REAPER honours that mid-render, dropping a note; the plugin opts out (`CLAP_RESTART_ON_RENDER_MODE_CHANGE = false`, [Lifecycle](#lifecycle)).
- **Editor close.** Stock nice-plug-egui 0.6.0 never calls `editor_closed`; the vendored fork does (lane FK). The shell uses it (end a drag, release auditions, forward the `End`s), still watches `is_open()` in `process()`, and treats every `build()` as a fresh open.
- **The vendored fork** (lane FK, `vendor/`): the plugin builds against it through `[patch.crates-io]`. It also fixes nice-plug's CLAP wrapper losing events that precede a splitting parameter event on the same frame under `SAMPLE_ACCURATE_AUTOMATION`.
- **Damaged fields.** Text that is not JSON never reaches a field's `set` (nice-plug refuses it, with a debug assertion that fires under `cfg(test)`); JSON that is not a patch loads the init patch and is kept as text until the first edit.
- **Unsupported sample rates** activate silent (above).
- **nice-plug's own input queue** grows (one allocation, permitted inside its wrapper and logged) when a host sends more than 1,024 events in a block; the plugin's list then renders in chunks. The engine drops events only past 4,096 waiting for one segment boundary.
